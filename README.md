# LAN Pong

Pong для двух игроков в одной локальной сети. Каждый игрок запускает приложение на своём компьютере и открывает локальную страницу в браузере. Компьютеры обмениваются игровыми пакетами напрямую через UDP; отдельный игровой сервер не нужен.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) на каждом компьютере.
- Node.js **20.19+** в ветке 20 или **22.12+** и pnpm **11.15.1** для разработки и сборки фронтенда.
- Оба компьютера в одной локальной сети. Выбранный игровой UDP-порт (по умолчанию **47777**) должен быть доступен на компьютере, который создаёт игру. Для автоматического поиска сеть должна пропускать локальный mDNS-трафик на UDP-порту **5353** или широковещательные UDP-пакеты на игровом порту.
- Современный браузер с поддержкой Canvas и WebSocket.

Игра использует .NET 10 и C# 14. UDP-пакеты и обмен с браузером через WebSocket используют MessagePack; HTTP API остаётся на JSON. C# тесты используют [TUnit](https://tunit.dev/docs/getting-started/installation/). Версии NuGet-пакетов заданы централизованно.

## Разработка фронтенда

Один раз установите зависимости из корня проекта:

```bash
pnpm install --frozen-lockfile
```

Запустите два процесса в отдельных терминалах:

```bash
# Терминал 1: API и WebSocket
dotnet run --project src/LanPong/LanPong.csproj --launch-profile Development

# Терминал 2: Vite
pnpm dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницу при изменении файлов в `frontend/` и пересылает запросы `/api` и `/ws` приложению .NET на `http://127.0.0.1:5080`. Если .NET запущен на другом адресе, задайте `LANPONG_DOTNET_URL` перед `pnpm dev`. В этом режиме браузер открывает адрес Vite.

Исходники страницы находятся в `frontend/index.html` и `frontend/src/`. Код приложения написан на TypeScript; Vite преобразует его для браузера в режиме разработки и при сборке. Команда `pnpm typecheck` проверяет типы отдельно, а `pnpm build` проверяет их перед сборкой и создаёт готовые файлы в `src/LanPong/wwwroot`; эту папку генерирует Vite, и она не хранится в Git. Для форматирования используйте `pnpm format`, для проверки формата — `pnpm format:check`.

## Сборка для запуска через .NET

Для запуска из исходников после установки зависимостей соберите статические файлы:

```bash
pnpm build
```

После этого `dotnet run` обслуживает страницу из `src/LanPong/wwwroot`. При изменении фронтенда повторите `pnpm build`. Для публикации приложения вместе со статическими файлами:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -o .artifacts/publish
```

`dotnet publish` сам выполняет `pnpm install --frozen-lockfile` и `pnpm build`, поэтому в публикацию попадают свежие файлы из `wwwroot`. На машине, где запускается уже опубликованное приложение, Node.js и pnpm не нужны.

## Запуск на двух компьютерах

В корне проекта `LanPong` выполните на **каждом** компьютере команды `pnpm install --frozen-lockfile` и `pnpm build`, затем запустите приложение:

```bash
dotnet run --project src/LanPong/LanPong.csproj -c Release
```

Откройте адрес `http://127.0.0.1:5080` **на том же компьютере**, где запущена команда.

1. Первый игрок нажимает **«Создать игру»**. Приложение покажет его локальные IP-адреса и UDP-порт.
2. Второй игрок нажимает **«Найти в сети»**. Поиск подставит IP и фактический UDP-порт найденной игры; при нескольких результатах выберите нужный. Затем нажмите **«Войти»**. Если игра не найдена, введите IP и порт первого компьютера вручную.
3. Управление ракеткой: **W/S** или **↑/↓**. На сенсорном экране есть экранные кнопки. Игра идёт до **7 очков**.

Удары ракетки и стен, подача и гол сопровождаются звуками и короткими эффектами на поле. После гола подсвечивается счёт забившей стороны. Звук можно выключить или настроить ползунком громкости; настройка сохраняется в браузере. Браузер включает воспроизведение звука после первого действия игрока.

Адрес `127.0.0.1` подходит только для проверки двух копий на одном компьютере. Для игры по сети второму игроку нужен другой IPv4-адрес из списка первого игрока, например `192.168.x.x`.

Автоматический поиск использует DNS-SD через mDNS и дополнительно прежний широковещательный UDP-запрос. mDNS находит игру даже на нестандартном UDP-порту; для широковещательного запроса используется порт из поля «UDP-порт» (или `47777`, если поле пустое или неверное). Поиск работает в пределах локального сетевого сегмента: изоляция клиентов Wi-Fi, настройки маршрутизатора или брандмауэра могут блокировать multicast и broadcast. Если игра не появляется в списке, подключитесь по IP вручную. Если подключение по IP тоже не происходит, проверьте доступность компьютеров и входящий UDP на игровом порту первого компьютера.

Для завершения приложения нажмите **Ctrl+C** в его терминале. Процесс сообщает сопернику о выходе, закрывает локальные WebSocket-соединения и освобождает UDP-порт. При принудительном завершении процесса без обработки сигнала соперник обнаружит потерю связи по обычному тайм-ауту.

## Проверка на одном компьютере

Сначала выполните `pnpm install --frozen-lockfile` и `pnpm build`. Затем откройте два терминала в папке проекта:

```bash
# Первый терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release

# Второй терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release --launch-profile Player2
```

Откройте `http://127.0.0.1:5080` и `http://127.0.0.1:5081` в двух окнах браузера. В первом создайте игру, во втором подключитесь к `127.0.0.1:47777`.

## Как устроена сеть

- Пока первый игрок ждёт подключения, его процесс объявляет службу `_lanpong._udp.local.` через DNS-SD/mDNS. Второй процесс ищет эту службу; запись SRV сообщает игровой UDP-порт, поэтому для mDNS не требуется заранее знать порт хоста. Браузер вызывает локальный HTTP `/api/discover`, получает пары IP/порт и заполняет форму. В качестве дополнительного способа процесс отправляет прежний `DiscoverPacket` широковещанием на указанный порт и принимает `OfferPacket`. После выбора игры соединение устанавливается обычным UDP-обменом `Hello`/`Welcome`; mDNS не передаёт игровые данные. Схему mDNS и DNS-SD определяют [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) и [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
- Локальная страница общается со своим процессом C# через WebSocket на `127.0.0.1`. Снимки состояния и команды управления передаются бинарными сообщениями MessagePack версии 2. HTTP-запросы `/api` сохраняют JSON и строковые значения роли, соединения и фазы. Профили `Player1` и `Player2` в `src/LanPong/Properties/launchSettings.json` запускают собранную страницу на портах 5080 и 5081. Первый профиль выбирается при обычном `dotnet run`; второй можно выбрать в Rider или параметром `--launch-profile Player2`. Профиль `Development` запускает API и WebSocket для Vite на порту 5080.
- Первый игрок слушает выбранный UDP-порт, второй использует свободный локальный порт. Между ними идёт прямой обмен бинарными пакетами MessagePack версии 5. Числовой тег `Union` определяет тип сообщения; фаза игры передаётся числовым значением enum. Для игры обе копии приложения должны использовать одинаковую версию UDP-протокола. Версии UDP и браузерного WebSocket независимы.
- Оба процесса рассчитывают физику с фиксированным шагом 1/60 с. Хост остаётся авторитетным и отправляет полное состояние примерно 30 раз в секунду. Гость прогнозирует игру между этими состояниями и повторно рассчитывает шаги после получения очередного состояния хоста.
- Гость отправляет для каждого шага номер такта и несколько последних направлений ракетки. Если ввод приходит на хост после соответствующего такта, хост восстанавливает сохранённое состояние и повторяет затронутые шаги с этим вводом. Окно отката ограничено 24 тактами (400 мс); более старый ввод не меняет уже рассчитанный результат. После потери отдельного UDP-пакета недавний ввод повторяется в следующих пакетах.
- Правила движения и нормализованная геометрия поля заданы в `src/LanPong/GameConstants.cs`; браузер повторяет нужные значения в `frontend/src/game.ts` для прогноза и рисования.
- Браузер получает текущее состояние своего процесса примерно 60 раз в секунду и рисует его через `requestAnimationFrame`. Между сообщениями он кратко продолжает движение мяча, останавливая прогноз у вероятного столкновения; небольшие исправления траектории сглаживаются. Своя ракетка откликается сразу на ввод. После гола, нового матча или переподключения история движения очищается. Из-за прогноза результат столкновения или счёт может быть кратко исправлен после прихода сетевого ввода.
- Сервер записывает последние 12 игровых событий с ID, номером такта и координатами. Хост передаёт их гостю в авторитетном UDP-состоянии, а оба процесса включают их в снимки WebSocket. Браузер воспроизводит подтверждённое событие один раз по его ID, даже если история приходит повторно или хост пересчитывает прошлые такты. След мяча и визуальная подсветка дополняют звуковой отклик.
- Статичный фон игрового поля кэшируется и обновляется при изменении размера Canvas.
- Строка **«Пинг»** показывает сглаженное время запроса и ответа между двумя игровыми процессами по UDP. Измерение обновляется примерно раз в секунду и становится пустым при потере соединения.
- Подключение повторяется до ответа. Запрос нового матча от второго игрока повторяется до получения нового состояния. Пакеты проверяются по адресу и идентификатору сеанса; ввод привязан к номеру матча и такту. Состояния хоста принимаются по возрастающему номеру такта.

Формат WebSocket версии 2 — массивы MessagePack с фиксированными позициями. Снимок содержит 21 элемент:

```text
[2, role, connection, message, udpPort, localAddresses, peerAddress,
 leftY, rightY, ballX, ballY, ballVx, ballVy, leftScore, rightScore,
 phase, countdown, tick, roundId, pingMs, recentEvents]
```

`recentEvents` — массив последних событий вида `[id, kind, tick, x, y]`. `id` — строка, `tick` — номер такта, `x` и `y` — нормализованные координаты поля от 0 до 1. Значения `kind`: `1` подача, `2` удар ракетки, `3` удар стены, `4` гол, `5` начало матча. Команда управления — `[2, axis]`, где `axis` равен `-1`, `0` или `1`. Числовые значения enum: `role` — `0` нет роли, `1` хост, `2` гость; `connection` — `0` ожидание действий, `1` ожидание игрока, `2` подключение, `3` подключено; `phase` — `0` ожидание, `1` отсчёт, `2` игра, `3` завершение. Начальное число `2` — версия браузерного протокола, которая не связана с версией UDP.

Игра предназначена для доверенной локальной сети. Решение `LanPong.slnx` находится в корне, C# приложение — в `src/LanPong`, исходники фронтенда — в `frontend`, а тесты — в `tests`. Общие настройки сборки заданы в `Directory.Build.props`. Версии NuGet-пакетов находятся в `Directory.Packages.props`.

## Тесты

Сначала выполните `pnpm install --frozen-lockfile`. Затем из корня проекта:

```bash
dotnet test --solution LanPong.slnx -c Release
pnpm typecheck
pnpm test:frontend
python3 tests/integration/integration_test.py
```

Первая команда запускает TUnit тесты столкновений, переходов между раундами, начисления очков, игровых событий, восстановления состояния и отката после позднего ввода через `Microsoft.Testing.Platform`, выбранную в `global.json`. Имена C# тестов следуют [формату](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) `Метод_WhenУсловие_ОжидаемыйРезультат`. Вторая проверяет типы TypeScript. Третья проверяет отображение текущего состояния, исправление траектории, локальный прогноз ракетки, отклик на события и кэш Canvas без браузера. Для четвёртой нужен Python 3; она собирает фронтенд и приложение, затем запускает две локальные копии для проверки UDP, WebSocket, передачи игровых событий, пинга, прогноза гостя при задержанных пакетах состояния, синхронизации, повторного матча и корректного завершения обоих игроков по SIGTERM. Проверка сети открывает локальные TCP-порты 5180 и 5181, UDP-порт 47888 и свободный локальный UDP-порт реле.

Для отдельной проверки mDNS на одном компьютере запустите `LANPONG_REQUIRE_MDNS_LOOPBACK=1 python3 tests/integration/integration_test.py`. Она ищет игру при заведомо неверном порту широковещательного запроса и проверяет снятие и повторное объявление службы. Совместное использование UDP-порта 5353 несколькими процессами на одной машине зависит от ОС, поэтому обычный интеграционный тест оставляет эту проверку выключенной.

Обоснование оптимизаций, источники и ограничения описаны в [RESEARCH.md](RESEARCH.md).
