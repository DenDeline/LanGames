# LAN Pong

Pong для двух игроков в одной локальной сети. Каждый игрок запускает приложение на своём компьютере и открывает локальную страницу в браузере. Компьютеры обмениваются игровыми пакетами напрямую через UDP; отдельный игровой сервер не нужен.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) на каждом компьютере.
- Node.js **20.19+** в ветке 20 или **22.12+** и pnpm **11.15.1** для разработки и сборки фронтенда.
- Оба компьютера в одной локальной сети. UDP-порт **47777** должен быть доступен на компьютере, который создаёт игру.
- Современный браузер с поддержкой Canvas и WebSocket.

Игра использует .NET 10 и C# 14. UDP-пакеты и обмен с браузером через WebSocket используют MessagePack; HTTP API остаётся на JSON. C# тесты используют [TUnit](https://tunit.dev/docs/getting-started/installation/). Версии NuGet-пакетов заданы централизованно.

## Разработка фронтенда

Один раз установите зависимости из корня проекта:

```bash
pnpm install --frozen-lockfile
```

Запустите два процесса в отдельных терминалах:

```bash
# Терминал 1: API и WebSocket
dotnet run --project src/LanPong/LanPong.csproj --launch-profile Development

# Терминал 2: Vite
pnpm dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницу при изменении файлов в `frontend/` и пересылает запросы `/api` и `/ws` приложению .NET на `http://127.0.0.1:5080`. Если .NET запущен на другом адресе, задайте `LANPONG_DOTNET_URL` перед `pnpm dev`. В этом режиме браузер открывает адрес Vite.

Исходники страницы находятся в `frontend/index.html` и `frontend/src/`. Код приложения написан на TypeScript; Vite преобразует его для браузера в режиме разработки и при сборке. Команда `pnpm typecheck` проверяет типы отдельно, а `pnpm build` проверяет их перед сборкой и создаёт готовые файлы в `src/LanPong/wwwroot`; эту папку генерирует Vite, и она не хранится в Git. Для форматирования используйте `pnpm format`, для проверки формата — `pnpm format:check`.

## Сборка для запуска через .NET

Для запуска из исходников после установки зависимостей соберите статические файлы:

```bash
pnpm build
```

После этого `dotnet run` обслуживает страницу из `src/LanPong/wwwroot`. При изменении фронтенда повторите `pnpm build`. Для публикации приложения вместе со статическими файлами:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -o .artifacts/publish
```

`dotnet publish` сам выполняет `pnpm install --frozen-lockfile` и `pnpm build`, поэтому в публикацию попадают свежие файлы из `wwwroot`. На машине, где запускается уже опубликованное приложение, Node.js и pnpm не нужны.

## Запуск на двух компьютерах

В корне проекта `LanPong` выполните на **каждом** компьютере команды `pnpm install --frozen-lockfile` и `pnpm build`, затем запустите приложение:

```bash
dotnet run --project src/LanPong/LanPong.csproj -c Release
```

Откройте адрес `http://127.0.0.1:5080` **на том же компьютере**, где запущена команда.

1. Первый игрок нажимает **«Создать игру»**. Приложение покажет его локальные IP-адреса и UDP-порт.
2. Второй игрок нажимает **«Найти в сети»** или вводит IP первого компьютера и порт `47777` вручную, затем нажимает **«Подключиться»**.
3. Управление ракеткой: **W/S** или **↑/↓**. На сенсорном экране есть экранные кнопки. Игра идёт до **7 очков**.

Адрес `127.0.0.1` подходит только для проверки двух копий на одном компьютере. Для игры по сети второму игроку нужен другой IPv4-адрес из списка первого игрока, например `192.168.x.x`.

Если автоматический поиск не находит игру, подключитесь по IP вручную. Поиск использует широковещательные UDP-пакеты, которые некоторые сети блокируют. Если подключение не происходит и по IP, проверьте, что компьютеры видят друг друга и брандмауэр первого компьютера разрешает входящий UDP на выбранном порту.

Для завершения приложения нажмите **Ctrl+C** в его терминале. Процесс сообщает сопернику о выходе, закрывает локальные WebSocket-соединения и освобождает UDP-порт. При принудительном завершении процесса без обработки сигнала соперник обнаружит потерю связи по обычному тайм-ауту.

## Проверка на одном компьютере

Сначала выполните `pnpm install --frozen-lockfile` и `pnpm build`. Затем откройте два терминала в папке проекта:

```bash
# Первый терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release

# Второй терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release --launch-profile Player2
```

Откройте `http://127.0.0.1:5080` и `http://127.0.0.1:5081` в двух окнах браузера. В первом создайте игру, во втором подключитесь к `127.0.0.1:47777`.

## Как устроена сеть

- Локальная страница общается со своим процессом C# через WebSocket на `127.0.0.1`. Снимки состояния и команды управления передаются бинарными сообщениями MessagePack версии 1. HTTP-запросы `/api` сохраняют JSON и строковые значения роли, соединения и фазы. Профили `Player1` и `Player2` в `src/LanPong/Properties/launchSettings.json` запускают собранную страницу на портах 5080 и 5081. Первый профиль выбирается при обычном `dotnet run`; второй можно выбрать в Rider или параметром `--launch-profile Player2`. Профиль `Development` запускает API и WebSocket для Vite на порту 5080.
- Первый игрок слушает выбранный UDP-порт, второй использует свободный локальный порт. Между ними идёт прямой обмен бинарными пакетами MessagePack версии 3. Числовой тег `Union` определяет тип сообщения; фаза игры передаётся числовым значением enum. Для игры обе копии приложения должны использовать одинаковую версию UDP-протокола. Версии UDP и браузерного WebSocket независимы.
- Первый игрок рассчитывает физику с фиксированным шагом 1/60 с и ограниченным догонянием после задержки игрового цикла. Столкновения определяются по времени контакта внутри шага. Второй игрок отправляет направление своей ракетки; первый отправляет полное состояние игры примерно 30 раз в секунду. Потерянный пакет состояния заменяется следующим.
- Правила движения и нормализованная геометрия поля заданы в `src/LanPong/GameConstants.cs`; браузер повторяет нужные значения в `frontend/src/game.ts` для прогноза и рисования.
- Браузер рисует мяч и чужую ракетку через `requestAnimationFrame` на одной временной шкале снимков. Буфер автоматически меняется примерно от 50 до 110 мс при изменении джиттера; краткий прогноз мяча ограничен 35 мс. Своя ракетка откликается сразу на ввод и мягко сверяется с состоянием хоста. После гола, нового раунда или переподключения история движения очищается.
- Статичный фон игрового поля кэшируется и обновляется при изменении размера Canvas.
- Строка **«Пинг»** показывает сглаженное время запроса и ответа между двумя игровыми процессами по UDP. Измерение обновляется примерно раз в секунду и становится пустым при потере соединения.
- Подключение повторяется до ответа. Запрос нового матча от второго игрока повторяется до получения нового состояния. Старые пакеты ввода и состояния отбрасываются по порядковому номеру; соединение проверяется по адресу и идентификатору сеанса.

Формат WebSocket версии 1 — массивы MessagePack с фиксированными позициями. Снимок содержит 20 элементов:

```text
[1, role, connection, message, udpPort, localAddresses, peerAddress,
 leftY, rightY, ballX, ballY, ballVx, ballVy, leftScore, rightScore,
 phase, countdown, tick, roundId, pingMs]
```

Команда управления — `[1, axis]`, где `axis` равен `-1`, `0` или `1`. Числовые значения enum: `role` — `0` нет роли, `1` хост, `2` гость; `connection` — `0` ожидание действий, `1` ожидание игрока, `2` подключение, `3` подключено; `phase` — `0` ожидание, `1` отсчёт, `2` игра, `3` завершение. Начальное число `1` — версия браузерного протокола, которая не связана с версией UDP.

Игра предназначена для доверенной локальной сети. Решение `LanPong.slnx` находится в корне, C# приложение — в `src/LanPong`, исходники фронтенда — в `frontend`, а тесты — в `tests`. Общие настройки сборки заданы в `Directory.Build.props`. Версии NuGet-пакетов находятся в `Directory.Packages.props`.

## Тесты

Сначала выполните `pnpm install --frozen-lockfile`. Затем из корня проекта:

```bash
dotnet test --solution LanPong.slnx -c Release
pnpm typecheck
pnpm test:frontend
python3 tests/integration/integration_test.py
```

Первая команда запускает TUnit тесты столкновений, переходов между раундами, начисления очков и повторяемости симуляции через `Microsoft.Testing.Platform`, выбранную в `global.json`. Имена C# тестов следуют [формату](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) `Метод_WhenУсловие_ОжидаемыйРезультат`. Вторая проверяет типы TypeScript. Третья проверяет интерполяцию, локальный прогноз ракетки и кэш Canvas без браузера. Для четвёртой нужен Python 3; она собирает фронтенд и приложение, затем запускает две локальные копии для проверки UDP, WebSocket, пинга, синхронизации, повторного матча и корректного завершения обоих игроков по SIGTERM. Проверка сети открывает локальные TCP и UDP порты 5180, 5181 и 47888.

Обоснование оптимизаций, источники и ограничения описаны в [RESEARCH.md](RESEARCH.md).
