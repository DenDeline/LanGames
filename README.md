# LAN Pong

Pong против выбранного бота на одном компьютере или для двух игроков в одной локальной сети. Каталог соперников задаётся в конфигурации приложения. В игре с ботом человек выбирает начальную сторону: слева, справа или случайно. В сетевой игре начальные стороны назначаются случайно при принятии подключения. После завершённого матча успешный реванш меняет стороны и с ботом, и в LAN. Для игры по сети каждый игрок запускает приложение на своём компьютере и открывает локальную страницу в браузере. Компьютеры обмениваются игровыми пакетами напрямую через UDP; отдельный игровой сервер не нужен.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) на машине разработки или сборки.
- Node.js **20.19+** в ветке 20 или **22.12+** и pnpm **11.15.1** для разработки и публикации фронтенда.
- Для игры с другом оба компьютера должны быть в одной локальной сети. Игровой UDP-порт выбирает ОС; входящий трафик на нём должен быть доступен на компьютере, который ожидает соперника. Для автоматического поиска сеть должна пропускать локальный mDNS-трафик на UDP-порту **5353**. Для игры с ботом сеть не требуется.
- Современный браузер с поддержкой Canvas и WebSocket.

Игра использует .NET 10 и C# 14. UDP-пакеты и обмен с браузером через WebSocket используют MessagePack; HTTP API остаётся на JSON. C# тесты используют [TUnit](https://tunit.dev/docs/getting-started/installation/). Версии NuGet-пакетов заданы централизованно.

## Разработка фронтенда

Один раз установите зависимости из корня проекта:

```bash
pnpm install --frozen-lockfile
```

Запустите два процесса в отдельных терминалах:

```bash
# Терминал 1: API и WebSocket
dotnet run --project src/LanPong/LanPong.csproj --launch-profile Development

# Терминал 2: Vite
pnpm dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницу при изменении файлов в `frontend/` и пересылает запросы `/api` и `/ws` приложению .NET на `http://127.0.0.1:5080`. Если .NET запущен на другом адресе, задайте `LANPONG_DOTNET_URL` перед `pnpm dev`. В этом режиме браузер открывает адрес Vite.

Исходники страницы находятся в `frontend/index.html` и `frontend/src/`. Код приложения написан на TypeScript; Vite преобразует его для браузера в режиме разработки и при сборке. Команда `pnpm typecheck` проверяет типы отдельно, а `pnpm build` проверяет их перед сборкой и создаёт готовые файлы в `src/LanPong/wwwroot`; эту папку генерирует Vite, и она не хранится в Git. Для форматирования используйте `pnpm format`, для проверки формата — `pnpm format:check`.

`frontend/src/game.ts` соединяет модули страницы: `snapshot.ts` разбирает HTTP-состояние, `wsProtocol.ts` — бинарный WebSocket, `session.ts` принимает снимки и проверяет их порядок, `motion.ts` рассчитывает отображаемое движение, `arena.ts` рисует Canvas, `feedback.ts` и `sound.ts` показывают и озвучивают события, `view.ts` обновляет интерфейс, а `input.ts` собирает управление. Стили разделены по областям страницы в `frontend/src/styles/` и подключаются через `style.css` в прежнем порядке.

## Сборка из исходников и публикация

Для запуска из исходников после установки зависимостей соберите статические файлы:

```bash
pnpm build
```

После этого `dotnet run` обслуживает страницу из `src/LanPong/wwwroot`. При изменении фронтенда повторите `pnpm build`. Для публикации приложения вместе со статическими файлами:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -o .artifacts/publish
```

`dotnet publish` сам выполняет `pnpm install --frozen-lockfile` и `pnpm build`, поэтому в публикацию попадают свежие файлы из `wwwroot`. По умолчанию он создаёт нативное self-contained приложение для ОС и архитектуры машины сборки. При необходимости укажите целевую архитектуру через `-r`, например `-r osx-arm64`; для другой ОС AOT-публикацию нужно выполнять на соответствующей ОС. Release-публикация не включает `appsettings.Development.json` и отдельные отладочные символы (`.pdb`, `.dbg`, `.dSYM`); символы остаются в каталоге сборки для диагностики. При повторном использовании `-o` сначала очистите каталог публикации от файлов предыдущей сборки. Для запуска опубликованного приложения .NET SDK, Node.js и pnpm не нужны.

### Проверка опубликованной игры и отдельная диагностика

Проверка публикации запускает обычное приложение и выбранного Вектора через HTTP API. Она сверяет SHA-256 `Models/hard-v1.onnx`, наличие нативной библиотеки ONNX Runtime, реальный переход в `Playing`, продвижение тиков каденции, движение ракетки и совпадающую идентичность бота в HTTP/WebSocket. Производственное приложение не содержит диагностических команд, отчётов или маленькой модели `aot-smoke.onnx`.

Из корня репозитория:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -r osx-arm64 -o .artifacts/publish/osx-arm64
python3 tests/integration/verify_publish_contents.py .artifacts/publish/osx-arm64
LANPONG_TEST_BINARY="$PWD/.artifacts/publish/osx-arm64/LanPong" python3 tests/integration/published_smoke_test.py
LANPONG_TEST_BINARY="$PWD/.artifacts/publish/osx-arm64/LanPong" python3 tests/integration/integration_test.py
```

Для разработчика есть отдельный managed-инструмент `tools/LanPong.BotDiagnostics` с `PublishAot=false`; он не запускает игровой peer или HTTP listener. Его маленькая модель проверяет вычисление `2 + 1 = 3`, а сохранённая команда `--bot-benchmark` проверяет настроенный профиль и выводит диагностический отчёт. Это собственный developer probe, а не BenchmarkDotNet. Команде `--onnx-smoke` передаётся только этот единственный аргумент. Для конфигурационного probe задавайте **абсолютный** content root с `appsettings.json` и моделями:

```bash
dotnet run --project tools/LanPong.BotDiagnostics -c Release -- --onnx-smoke
dotnet run --project tools/LanPong.BotDiagnostics -c Release -- --bot-benchmark vektor --environment Production --contentRoot "$PWD/src/LanPong"
dotnet build tools/LanPong.BotDiagnostics/LanPong.BotDiagnostics.csproj -c Release
LANPONG_DIAGNOSTICS_DLL="$PWD/tools/LanPong.BotDiagnostics/bin/Release/net10.0/LanPong.BotDiagnostics.dll" python3 tests/integration/bot_diagnostics_smoke_test.py
python3 tests/integration/verify_production_boundary.py
```

Разделение инструмента и production, параметры probe и миграция протоколов описаны в [текущем руководстве](docs/bot-runtime-cleanup/current-guide.md). Workflow выпуска настроен на smoke после публикации для `osx-arm64`, `linux-x64` и `win-x64`, а на macOS и Linux — также на полную интеграцию против опубликованного файла. Локальное выполнение текущей версии подтверждено только на macOS ARM64; известные предупреждения MessagePack `IL3053` (AOT) и `IL2104` (trimming) сохраняются.

Историческая ранняя проверка 8 октября 2026 года на macOS ARM64 с .NET SDK 10.0.400 дала архив очищенной публикации **20 408 175 байт** против **31 106 656 байт** у предыдущего архива с `LanPong.dSYM` и `appsettings.Development.json`. Эти размеры относятся к той сборке, а не к текущей публикации.

## Выпуски на GitHub

При push тега `v*` GitHub Actions сначала запускает тесты, затем публикует Native AOT приложение на macOS ARM64, Windows x64 и Linux x64. После проверки опубликованных приложений workflow создаёт GitHub Release и прикрепляет `LanPong-osx-arm64.tar.gz`, `LanPong-win-x64.zip` и `LanPong-linux-x64.tar.gz`. Перед упаковкой workflow проверяет отсутствие development-конфига и отладочных символов. Каждый архив содержит весь каталог публикации, включая страницу игры. Например, для выпуска `v1.0.0`:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Теги с суффиксом вроде `v1.0.0-rc.1` создают предварительный релиз. Публикация релиза вручную также запускает сборку и добавляет недостающие архивы. Если в репозитории включены неизменяемые релизы GitHub, используйте выпуск через push тега: архивы прикрепляются при создании релиза, до его публикации. Повторный запуск пропускает релиз, когда все три архива уже прикреплены. Linux-сборка создаётся на Ubuntu 24.04 и требует совместимой версии системных библиотек; macOS-сборка не подписана сертификатом Apple.

## Игра против бота на одном компьютере

Запустите приложение и откройте его страницу в браузере на том же компьютере. В компактном списке **«Режим игры»** выберите **«Против бота»**, введите ник и выберите **«Начальную сторону»**: **«Слева»** по умолчанию, **«Справа»** или **«Случайно»**. Случайная сторона определяется сервером один раз при успешном запуске. Начальное предпочтение сохраняется в текущей открытой вкладке при смене режима, реваншах и выходе; приложение не сохраняет его между перезагрузками страницы. Оно отдельно от текущей стороны: после запуска справа и реванша слева следующий новый матч по-прежнему начинается с предпочтения «Справа».

Панель показывает краткую сводку выбранного соперника. Кнопка **«Изменить»** открывает каталог с описаниями, стилем, сложностью и доступностью; в комплекте есть **Лада**, **Искра** и **Вектор**. В окне выбора используются обычные переключатели: Tab переводит фокус, стрелки меняют выбор. Выбор применяется сразу; **«Готово»**, **«Закрыть»** и Escape возвращают компактную панель и фокус к кнопке открытия, не запуская игру. Одна кнопка **Играть с «имя»** запускает матч; при ещё не проверенной замене она может предлагать **Попробовать «имя»**. Во время запуска и активной сессии выбор режима, ника, бота и начальной стороны заблокирован.

Матч начинается после отсчёта и идёт до **7 очков**. Вы управляете своей назначенной ракеткой клавишами **W/S** или **↑/↓**, либо экранными кнопками на сенсорном устройстве. Подпись стороны и имена у счёта показывают фактическое владение левой или правой ракеткой; бот занимает противоположную сторону. Успешный запуск переводит фокус на поле. Подключение к другому компьютеру и UDP-порт не нужны; адреса и сетевой пинг не показываются.

Если выбранный бот недоступен, играть можно только при наличии доступной настроенной замены. Профиль объясняет известную замену ещё до запуска; если ошибка обнаружится при подготовке модели или во время игры, уведомление показывает выбранного и фактического соперника. У Вектора в исходной конфигурации замена — Лада. Уведомление сохраняется при реванше. Без доступной замены запуск отклоняется, а отказ уже играющего бота завершает локальную сессию с сообщением.

После подтверждённого завершения нажмите **Реванш с «имя»**: он сохраняет выбранный профиль и сессию, меняет стороны один раз и начинает новый матч со счёта 0:0. Если бот откажет при подготовке реванша, возможен переход на явно настроенную замену; интерфейс показывает фактического соперника и причину. Интерфейс показывает вашу следующую сторону только при доступном реванше. До его успешного принятия имена и итоговый счёт остаются на завершённых физических сторонах. **«К выбору игры»** завершает матч и убирает уведомление о замене. Выбранный бот остаётся выбранным в открытой вкладке, пока доступен для запуска. Затем можно выбрать другого бота, **«Быструю игру по сети»** или **«Присоединиться по сети»**. При ошибке загрузки каталога доступна кнопка **«Повторить»**; сетевые действия остаются доступны.

Настройка каталога и полный пример четвёртого бота находятся в [руководстве по конфигурации](docs/bot-catalog/configuration.md); текущие инструменты, v9 и переход с прежнего API — в [руководстве по инструментам и миграции](docs/bot-runtime-cleanup/current-guide.md). Изменения настроек требуют перезапуска приложения. [Первоначальные измерения runtime](docs/bot-catalog/performance.md) сохранены как исторические результаты со своими командами и ограничениями.

Схема наблюдений обучаемого бота, генератор данных и проверка Teacher против Simple описаны в [BOT_TRAINING_DATA.md](docs/bots/BOT_TRAINING_DATA.md). Обучение и экспорт ONNX описаны в [BOT_MODEL.md](docs/bots/BOT_MODEL.md). Первоначальное встраивание модели и результаты прежнего Hard сохранены как историческая проверка в [BOT_HARD_RUNTIME.md](docs/bots/BOT_HARD_RUNTIME.md).

## Запуск на двух компьютерах

Скачайте и распакуйте архив своей платформы из GitHub Releases или скопируйте содержимое `.artifacts/publish` на компьютеры с подходящей ОС и архитектурой. В папке с опубликованным приложением запустите его на **каждом** компьютере:

```bash
./LanPong --urls http://127.0.0.1:5080
```

В Windows запустите `LanPong.exe` с тем же параметром. Для запуска из исходников на каждом компьютере по-прежнему можно выполнить `pnpm install --frozen-lockfile`, `pnpm build` и `dotnet run --project src/LanPong/LanPong.csproj -c Release`.

Откройте адрес `http://127.0.0.1:5080` **на том же компьютере**, где запущена команда.

Локальная страница по умолчанию слушает `127.0.0.1`; это не ограничивает IPv6-соединение между игровыми процессами. Если страницу нужно открывать по IPv6, настройте привязку ASP.NET Core к `::1` или нужному IPv6-адресу.

1. Каждый игрок вводит свой ник. Он сохраняется в браузере для следующих партий.
2. Каждый выбирает режим **«Быстрая игра по сети»** и нажимает **«Быстрая игра»**. Приложение ищет ожидающие игры в локальной сети и выбирает случайную. Если никого нет, оно само открывает игру на свободном UDP-порту и ждёт соперника. Матч начинается автоматически после подключения второго игрока.
3. Чтобы подключиться к конкретному другу, выберите режим **«Присоединиться по сети»**: найдите его игру по нику или введите адрес и порт вручную. На ожидающем устройстве адрес и выбранный порт находятся в разделе ручного подключения.
4. При принятии подключения хост случайно выбирает начальные стороны. Хост и гость — сетевые роли, каждая может управлять слева или справа; свою сторону смотрите по подписи и именам у счёта. Управление своей ракеткой: **W/S** или **↑/↓**; на сенсорном экране есть экранные кнопки. Игра идёт до **7 очков**. Выбор начальной стороны в LAN скрыт.

Подтверждённый завершённый матч допускает реванш со сменой сторон. Гость может ещё ждать подтверждения следующего раунда: до него сохраняются имена и завершённый счёт в исходном расположении. Предсказанное гостем завершение без подтверждения хоста показывает «Проверяем результат» и не разрешает реванш. После принятия нового раунда счёт и управление сбрасываются, а стороны меняются один раз.

Если один из игроков покидает быструю игру, матч и временное лобби закрываются у обоих. Для новой партии снова нажмите **«Быстрая игра»** или подключитесь к другу вручную. Если сообщение о выходе не дошло по UDP, второй игрок выйдет после 5 секунд без связи.

Входящий вызов сопровождается коротким звуковым сигналом для первого игрока. Удары ракетки и стен, подача и гол сопровождаются звуками и короткими эффектами на поле. После гола подсвечивается счёт забившей стороны. Звук можно выключить или настроить ползунком громкости; настройка сохраняется в браузере. Браузер включает воспроизведение звука после первого действия игрока.

Адреса `127.0.0.1` и `::1` подходят только для проверки двух копий на одном компьютере. Для игры по сети второму игроку нужен адрес первого компьютера из списка в приложении: IPv4, например `192.168.x.x`, или IPv6. Адрес IPv6 вводится в поле без квадратных скобок. Если используется link-local IPv6 (`fe80::…`), второму игроку нужна зона **его собственного** сетевого интерфейса, например `%en0` или `%3`; зона из списка адресов первого компьютера может отличаться. Автоматический поиск mDNS подставляет зону принимающего интерфейса сам.

Автоматический поиск использует DNS-SD через mDNS по IPv4 (`224.0.0.251`) и IPv6 (`ff02::fb`) и получает назначенный приложением игровой UDP-порт из объявления. Он работает в пределах локального сетевого сегмента: изоляция клиентов Wi-Fi, настройки маршрутизатора или брандмауэра могут блокировать multicast. Если игра не появляется в списке, подключитесь по IP и порту вручную. Если подключение по IP тоже не происходит, проверьте доступность компьютеров и входящий UDP на игровом порту первого компьютера.

Для завершения приложения нажмите **Ctrl+C** в его терминале. Процесс сообщает сопернику о выходе, закрывает локальные WebSocket-соединения и освобождает UDP-порт. При принудительном завершении процесса без обработки сигнала соперник обнаружит потерю связи по обычному тайм-ауту.

## Проверка на одном компьютере

Сначала выполните `pnpm install --frozen-lockfile` и `pnpm build`. Затем откройте два терминала в папке проекта:

```bash
# Первый терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release

# Второй терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release --launch-profile Player2
```

Откройте `http://127.0.0.1:5080` и `http://127.0.0.1:5081` в двух окнах браузера. Выберите режим **«Быстрая игра по сети»** и нажмите **«Быстрая игра»** в обоих окнах. Для проверки ручного подключения нажмите её только в первом окне, раскройте адрес и порт, затем введите их во втором окне в режиме **«Присоединиться по сети»**.

## Как устроена сеть

- Пока игрок ждёт подключения, его процесс объявляет службу `_lanpong._udp.local.` через DNS-SD/mDNS по IPv4 и IPv6. Запись SRV сообщает выбранный ОС игровой UDP-порт, записи A и AAAA — адреса, а TXT — версию протокола и ник хоста. Кнопка **«Быстрая игра»** запускает поиск через локальный backend: из найденных игр случайно выбирается одна, а при отсутствии свободных игр устройство начинает ожидать соперника. Если два игрока начинают поиск одновременно, идентификатор экземпляра mDNS определяет, кто оставит открытую игру, а кто присоединится к ней. Для выбора конкретного игрока браузер вызывает `/api/discover` и показывает ники найденных игр. При подключении гость отправляет UDP `Hello` с ID вызова и своим ником. Игра, запущенная через **«Быстрая игра»**, принимает вызов автоматически; mDNS не передаёт игровые данные. Схему mDNS и DNS-SD определяют [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) и [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
- Локальная страница общается со своим процессом C# через WebSocket на `127.0.0.1`. Снимки состояния и команды управления передаются бинарными сообщениями MessagePack версии **9**. HTTP-запросы `/api` сохраняют JSON и строковые значения роли, соединения, фазы и режима соперника; снимки содержат `version: 9`. Браузер получает каталог через `GET /api/bots`, затем отправляет `POST /api/local-opponent` с обязательными `nickname`, `botId` и `side`, например `{"nickname":"Игрок","botId":"iskra","side":"left"}`. Значение ID чувствительно к регистру: `iskra` и `Iskra` — разные значения. Отсутствие ID или стороны, как и старый запрос только с `mode: "simple"`/`"hard"`, приводит к HTTP 400; выбор по умолчанию из каталога выполняет клиент, а не этот endpoint. Перед новым запуском нужно покинуть текущую игру через `POST /api/leave`. Тот же процесс рассчитывает обе ракетки без игрового UDP-соединения. Профили `Player1` и `Player2` в `src/LanPong/Properties/launchSettings.json` запускают собранную страницу на портах 5080 и 5081. Первый профиль выбирается при обычном `dotnet run`; второй можно выбрать в Rider или параметром `--launch-profile Player2`. Профиль `Development` запускает API и WebSocket для Vite на порту 5080.
- Ожидающий игрок слушает назначенный ОС UDP-порт по IPv4 и IPv6, второй использует свободный локальный порт и выбранное семейство адресов. Между ними идёт прямой обмен бинарными пакетами MessagePack версии 9. Идентификаторы вызова, сеанса и перезапуска передаются как 16-байтные `Guid` через `NativeGuidResolver`; пустые идентификаторы отклоняются. Числовой тег `Union` определяет тип сообщения; фаза игры передаётся числовым значением enum. Для игры обе копии приложения должны использовать одинаковую версию UDP-протокола. UDP и браузерный WebSocket — отдельные протоколы, оба сейчас версии 9.
- Оба процесса рассчитывают физику с фиксированным шагом 1/60 с. Хост остаётся авторитетным и отправляет полное состояние примерно 30 раз в секунду. Гость прогнозирует игру между этими состояниями и повторно рассчитывает шаги после получения очередного состояния хоста.
- Гость отправляет для каждого шага номер такта и несколько последних направлений ракетки. Если ввод приходит на хост после соответствующего такта, хост восстанавливает сохранённое состояние и повторяет затронутые шаги с этим вводом. Окно отката ограничено 24 тактами (400 мс); более старый ввод не меняет уже рассчитанный результат. После потери отдельного UDP-пакета недавний ввод повторяется в следующих пакетах.
- Правила движения и нормализованная геометрия поля заданы в `src/LanPong/GameConstants.cs`; браузер повторяет нужные значения в `frontend/src/motion.ts` для прогноза и рисования.
- Браузер получает текущее состояние своего процесса примерно 60 раз в секунду и рисует его через `requestAnimationFrame`. Между сообщениями он кратко продолжает движение мяча, останавливая прогноз у вероятного столкновения; небольшие исправления траектории сглаживаются. Своя ракетка откликается сразу на ввод, а исправления позиций ракеток после отката плавно отображаются в течение 80 мс без изменения игровой симуляции. После гола, нового матча или переподключения история движения очищается. Из-за прогноза результат столкновения или счёт может быть кратко исправлен после прихода сетевого ввода.
- Сервер записывает последние 12 игровых событий с ID, номером такта и координатами. Хост передаёт их гостю в авторитетном UDP-состоянии, а оба процесса включают их в снимки WebSocket. Браузер воспроизводит подтверждённое событие один раз по его ID, даже если история приходит повторно или хост пересчитывает прошлые такты. След мяча и визуальная подсветка дополняют звуковой отклик.
- Статичный фон игрового поля кэшируется и обновляется при изменении размера Canvas.
- Строка **«Пинг»** показывает сглаженное время запроса и ответа между двумя игровыми процессами по UDP. Измерение обновляется примерно раз в секунду и становится пустым при потере соединения.
- После нажатия «Подключиться» запрос вызова повторяется до ответа. Если ответа нет 10 секунд, подключение завершается. Ожидающий вызов истекает через 2 минуты или после 5 секунд без пакетов от соперника. Если уже установленная связь пропала на 5 секунд, гостевая сессия завершается и для новой игры нужен повторный вход вручную. Запрос подтверждённого нового раунда от второго игрока повторяется до получения нового состояния. Пакеты вызова проверяются по ID и адресу, а игровые пакеты — по адресу и идентификатору сеанса; ввод привязан к положительному номеру раунда и такту. Состояния хоста принимаются по возрастающему номеру такта внутри текущего раунда.

HTTP API, каталог, браузерный WebSocket и UDP используют версию **9**. Формат браузерного снимка — MessagePack-массив с **35 элементами**:

```text
[9, role, connection, message, udpPort, localAddresses, peerAddress,
 leftY, rightY, ballX, ballY, ballVx, ballVy, leftScore, rightScore,
 phase, countdown, tick, roundId, pingMs, recentEvents, localNickname, peerNickname,
 opponentMode, requestedBotId, requestedBotName, effectiveBotId, effectiveBotName,
 opponentFallbackActive, botFallbackReason, localSide, matchId, sourceId,
 snapshotSequence, canRematch]
```

`recentEvents` — массив последних событий вида `[id, kind, tick, x, y]`. `id` — строка, `tick` — номер такта, `x` и `y` — нормализованные координаты поля от 0 до 1. Значения `kind`: `1` подача, `2` удар ракетки, `3` удар стены, `4` гол, `5` начало матча. Числовые значения enum: `role` — `0` нет роли, `1` хост, `2` гость; `connection` — `0` ожидание действий, `1` ожидание игрока, `2` подключение, `3` подключено, `4` входящий вызов, `5` ожидание принятия, `6` поиск соперника; `phase` — `0` ожидание, `1` отсчёт, `2` игра, `3` завершение; `opponentMode` — `0` нет соперника, `1` игра по сети, `2` локальный бот. В HTTP API `opponentMode` принимает строки `none`, `lan`, `bot`.

Хвост снимка: индекс 30 — `localSide` (`nil`/1/2 для отсутствия стороны/левой/правой; в JSON `null`/`left`/`right`), 31 — `matchId`, 32 — `sourceId`, 33 — `snapshotSequence`, 34 — обязательный boolean `canRematch`. До назначения `localSide` и `matchId` равны `null`. ID матча — нормализованная строка из 32 строчных hex-символов. `sourceId` обозначает время жизни локального `PongPeer` и различается у хоста и гостя; `snapshotSequence` возрастает при каждом захвате состояния под блокировкой. Вместе они упорядочивают HTTP/WebSocket независимо от физического тика и защищают от задержанных ответов старого процесса или контекста.

Управление — одно MessagePack-значение `[9, matchId, roundId, axis]`, где `roundId` положителен, а `axis` равен `-1`, `0` или `1`. Старый матч или раунд не может управлять новой назначенной ракеткой. `POST /api/local-opponent` требует `nickname`, `botId` и `side` ровно `left`, `right` или `random`; `POST /api/restart` — текущие `{matchId, expectedRoundId}` и подтверждённое завершение с `canRematch=true`. Подробнее о pending-ответе гостя и обработке коррекции — в [контракте и миграции](docs/bot-runtime-cleanup/current-guide.md).

`requestedBotId`/`requestedBotName` сохраняют выбор игрока, а `effectiveBotId`/`effectiveBotName` обозначают фактически играющего бота. `opponentFallbackActive` и безопасная причина `botFallbackReason` описывают настроенную замену; без замены причина равна `null`. При выходе и в LAN-сессии четыре поля ID/имени и `botFallbackReason` равны `null`, а `opponentFallbackActive` равен `false`. Обновляйте приложение, браузер и все LAN-клиенты совместно, перезагружая старые вкладки: UDP v9 передаёт сторону хоста и текущий раунд в Welcome, сторону хоста в State и ожидаемый раунд в Restart. Старые форматы v7/v8, `requestedOpponentMode` и публичные режимы `simple`/`hard` больше не поддерживаются.

Игра предназначена для доверенной локальной сети. Решение `LanPong.slnx` находится в корне, C# приложение — в `src/LanPong`, исходники фронтенда — в `frontend`, а тесты — в `tests`. Общие настройки сборки заданы в `Directory.Build.props`. Версии NuGet-пакетов находятся в `Directory.Packages.props`.

## Тесты

Сначала выполните `pnpm install --frozen-lockfile`. Затем из корня проекта:

```bash
dotnet test --solution LanPong.slnx -c Release
pnpm typecheck
pnpm test:frontend
python3 tests/integration/integration_test.py
```

Первая команда запускает TUnit тесты физики, событий, отката, конфигурации, runtime и жизненного цикла ботов через `Microsoft.Testing.Platform`, выбранную в `global.json`. Имена C# тестов следуют [формату](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) `Метод_WhenУсловие_ОжидаемыйРезультат`. Вторая проверяет типы TypeScript. Третья проверяет отображение состояния, движение, ввод, события, каталог и v9 HTTP/MessagePack без браузера. Для четвёртой нужен Python 3; она собирает фронтенд и приложение, затем проверяет настроенных ботов, добавленного только конфигурацией четвёртого бота, его параметры, выбранную и случайную сторону, завершённые реванши со сменой сторон, ограждение старого управления, выход и явную замену при отсутствующей или повреждённой модели. Две локальные копии проверяют IPv4 и, если доступен IPv6 loopback, IPv6 UDP, WebSocket, игровые события, пинг, прогноз гостя, синхронизацию, восстановление после потерянных Welcome, повторный матч, быструю игру и корректное завершение по SIGTERM. Проверка открывает локальные TCP-порты 5180–5183, UDP-порты 47888 и 47889 для ручного API и настроенного LAN-сценария, а также свободные UDP-порты для быстрой игры и реле.

Для отдельной проверки mDNS на одном компьютере запустите `LANPONG_REQUIRE_MDNS_LOOPBACK=1 python3 tests/integration/integration_test.py`. Она ищет игру через mDNS, проверяет снятие и повторное объявление службы, подключение к доступной быстрой игре и одновременный запуск поиска двумя игроками. Совместное использование UDP-порта 5353 несколькими процессами на одной машине зависит от ОС, поэтому обычный интеграционный тест оставляет эту проверку выключенной.

Чтобы прогнать тот же интеграционный сценарий против опубликованного Native AOT приложения на macOS или Linux, укажите путь к исполняемому файлу в `LANPONG_TEST_BINARY`; повторная сборка при этом не выполняется:

```bash
LANPONG_TEST_BINARY=/path/to/LanPong python3 tests/integration/integration_test.py
```

Последняя техническая проверка 8 октября 2026 года: **215 .NET тестов**, frontend behavior/input/v9 protocol, typecheck/build/format, source-интеграция и полная интеграция свежей Native AOT публикации, реальная published Vektor HTTP/WebSocket smoke и отдельные managed tool/production-boundary проверки прошли. Браузерная проверка охватывает desktop 1366/1024 px и телефоны 320/390 px, Left/Right/Random, два завершённых реванша со сменой сторон, отпускание/новое нажатие управления, режимы и окно выбора. Независимая проверка в браузере подтвердила native keyboard выбор и реальную игру с Вектором. Эта браузерная проверка и неизменённая training parity сохранены из предыдущих принятых этапов.
