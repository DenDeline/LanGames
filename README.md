# LAN Pong

Pong для двух игроков в одной локальной сети. Каждый игрок запускает приложение на своём компьютере и открывает локальную страницу в браузере. Компьютеры обмениваются игровыми пакетами напрямую через UDP; отдельный игровой сервер не нужен.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) на каждом компьютере.
- Node.js **20.19+** в ветке 20 или **22.12+** и pnpm **11.15.1** для разработки и сборки фронтенда.
- Оба компьютера в одной локальной сети. Выбранный игровой UDP-порт (по умолчанию **47777**) должен быть доступен на компьютере, который создаёт игру. Для автоматического поиска сеть должна пропускать локальный mDNS-трафик на UDP-порту **5353**.
- Современный браузер с поддержкой Canvas и WebSocket.

Игра использует .NET 10 и C# 14. UDP-пакеты и обмен с браузером через WebSocket используют MessagePack; HTTP API остаётся на JSON. C# тесты используют [TUnit](https://tunit.dev/docs/getting-started/installation/). Версии NuGet-пакетов заданы централизованно.

## Разработка фронтенда

Один раз установите зависимости из корня проекта:

```bash
pnpm install --frozen-lockfile
```

Запустите два процесса в отдельных терминалах:

```bash
# Терминал 1: API и WebSocket
dotnet run --project src/LanPong/LanPong.csproj --launch-profile Development

# Терминал 2: Vite
pnpm dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницу при изменении файлов в `frontend/` и пересылает запросы `/api` и `/ws` приложению .NET на `http://127.0.0.1:5080`. Если .NET запущен на другом адресе, задайте `LANPONG_DOTNET_URL` перед `pnpm dev`. В этом режиме браузер открывает адрес Vite.

Исходники страницы находятся в `frontend/index.html` и `frontend/src/`. Код приложения написан на TypeScript; Vite преобразует его для браузера в режиме разработки и при сборке. Команда `pnpm typecheck` проверяет типы отдельно, а `pnpm build` проверяет их перед сборкой и создаёт готовые файлы в `src/LanPong/wwwroot`; эту папку генерирует Vite, и она не хранится в Git. Для форматирования используйте `pnpm format`, для проверки формата — `pnpm format:check`.

`frontend/src/game.ts` соединяет модули страницы: `snapshot.ts` разбирает HTTP-состояние, `wsProtocol.ts` — бинарный WebSocket, `session.ts` принимает снимки и проверяет их порядок, `motion.ts` рассчитывает отображаемое движение, `arena.ts` рисует Canvas, `feedback.ts` и `sound.ts` показывают и озвучивают события, `view.ts` обновляет интерфейс, а `input.ts` собирает управление. Стили разделены по областям страницы в `frontend/src/styles/` и подключаются через `style.css` в прежнем порядке.

## Сборка для запуска через .NET

Для запуска из исходников после установки зависимостей соберите статические файлы:

```bash
pnpm build
```

После этого `dotnet run` обслуживает страницу из `src/LanPong/wwwroot`. При изменении фронтенда повторите `pnpm build`. Для публикации приложения вместе со статическими файлами:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -o .artifacts/publish
```

`dotnet publish` сам выполняет `pnpm install --frozen-lockfile` и `pnpm build`, поэтому в публикацию попадают свежие файлы из `wwwroot`. На машине, где запускается уже опубликованное приложение, Node.js и pnpm не нужны.

## Запуск на двух компьютерах

В корне проекта `LanPong` выполните на **каждом** компьютере команды `pnpm install --frozen-lockfile` и `pnpm build`, затем запустите приложение:

```bash
dotnet run --project src/LanPong/LanPong.csproj -c Release
```

Откройте адрес `http://127.0.0.1:5080` **на том же компьютере**, где запущена команда.

Локальная страница по умолчанию слушает `127.0.0.1`; это не ограничивает IPv6-соединение между игровыми процессами. Если страницу нужно открывать по IPv6, настройте привязку ASP.NET Core к `::1` или нужному IPv6-адресу.

1. Первый игрок нажимает **«Создать игру»**. Приложение покажет его локальные IP-адреса и UDP-порт.
2. Второй игрок нажимает **«Найти в сети»**. Поиск подставит IP и фактический UDP-порт найденной игры; при нескольких результатах выберите нужный. Затем нажмите **«Подключиться»**. Если игра не найдена, введите IP и порт первого компьютера вручную.
3. Первый игрок видит входящий вызов с адресом соперника и нажимает **«Принять»** или **«Отклонить»**. До принятия матч не начинается. Второй игрок может нажать **«Отменить вызов»**, пока ждёт ответа.
4. Управление ракеткой: **W/S** или **↑/↓**. На сенсорном экране есть экранные кнопки. Игра идёт до **7 очков**.

Если первый игрок нажимает **«Покинуть игру»**, второй автоматически выходит из игры. Для входа в новое лобби ему нужно снова нажать **«Подключиться»**. Если сообщение о выходе не дошло по UDP, второй игрок выйдет после 5 секунд без связи.

Входящий вызов сопровождается коротким звуковым сигналом для первого игрока. Удары ракетки и стен, подача и гол сопровождаются звуками и короткими эффектами на поле. После гола подсвечивается счёт забившей стороны. Звук можно выключить или настроить ползунком громкости; настройка сохраняется в браузере. Браузер включает воспроизведение звука после первого действия игрока.

Адреса `127.0.0.1` и `::1` подходят только для проверки двух копий на одном компьютере. Для игры по сети второму игроку нужен адрес первого компьютера из списка в приложении: IPv4, например `192.168.x.x`, или IPv6. Адрес IPv6 вводится в поле без квадратных скобок. Если используется link-local IPv6 (`fe80::…`), второму игроку нужна зона **его собственного** сетевого интерфейса, например `%en0` или `%3`; зона из списка адресов первого компьютера может отличаться. Автоматический поиск mDNS подставляет зону принимающего интерфейса сам.

Автоматический поиск использует DNS-SD через mDNS по IPv4 (`224.0.0.251`) и IPv6 (`ff02::fb`) и находит игру независимо от значения поля «UDP-порт». Он работает в пределах локального сетевого сегмента: изоляция клиентов Wi-Fi, настройки маршрутизатора или брандмауэра могут блокировать multicast. Если игра не появляется в списке, подключитесь по IP и порту вручную. Если подключение по IP тоже не происходит, проверьте доступность компьютеров и входящий UDP на игровом порту первого компьютера.

Для завершения приложения нажмите **Ctrl+C** в его терминале. Процесс сообщает сопернику о выходе, закрывает локальные WebSocket-соединения и освобождает UDP-порт. При принудительном завершении процесса без обработки сигнала соперник обнаружит потерю связи по обычному тайм-ауту.

## Проверка на одном компьютере

Сначала выполните `pnpm install --frozen-lockfile` и `pnpm build`. Затем откройте два терминала в папке проекта:

```bash
# Первый терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release

# Второй терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release --launch-profile Player2
```

Откройте `http://127.0.0.1:5080` и `http://127.0.0.1:5081` в двух окнах браузера. В первом создайте игру, во втором подключитесь к `127.0.0.1:47777` или `::1` с портом `47777`, затем примите вызов в первом окне.

## Как устроена сеть

- Пока первый игрок ждёт подключения, его процесс объявляет службу `_lanpong._udp.local.` через DNS-SD/mDNS по IPv4 и IPv6. Второй процесс ищет эту службу; запись SRV сообщает игровой UDP-порт, а записи A и AAAA — адреса, поэтому заранее знать порт хоста не требуется. Браузер вызывает локальный HTTP `/api/discover`, получает пары IP/порт и заполняет форму. После выбора игры гость отправляет UDP `Hello` с ID вызова, хост показывает запрос и отвечает `ChallengePending`. Только после нажатия **«Принять»** хост запускает матч и отправляет `Welcome`; mDNS не передаёт игровые данные. Схему mDNS и DNS-SD определяют [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) и [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
- Локальная страница общается со своим процессом C# через WebSocket на `127.0.0.1`. Снимки состояния и команды управления передаются бинарными сообщениями MessagePack версии 3. HTTP-запросы `/api` сохраняют JSON и строковые значения роли, соединения и фазы. Профили `Player1` и `Player2` в `src/LanPong/Properties/launchSettings.json` запускают собранную страницу на портах 5080 и 5081. Первый профиль выбирается при обычном `dotnet run`; второй можно выбрать в Rider или параметром `--launch-profile Player2`. Профиль `Development` запускает API и WebSocket для Vite на порту 5080.
- Первый игрок слушает выбранный UDP-порт по IPv4 и IPv6, второй использует свободный локальный порт и выбранное семейство адресов. Между ними идёт прямой обмен бинарными пакетами MessagePack версии 7. Идентификаторы вызова, сеанса и перезапуска передаются как 16-байтные `Guid` через `NativeGuidResolver`; пустые идентификаторы отклоняются. Числовой тег `Union` определяет тип сообщения; фаза игры передаётся числовым значением enum. Для игры обе копии приложения должны использовать одинаковую версию UDP-протокола. Версии UDP и браузерного WebSocket независимы.
- Оба процесса рассчитывают физику с фиксированным шагом 1/60 с. Хост остаётся авторитетным и отправляет полное состояние примерно 30 раз в секунду. Гость прогнозирует игру между этими состояниями и повторно рассчитывает шаги после получения очередного состояния хоста.
- Гость отправляет для каждого шага номер такта и несколько последних направлений ракетки. Если ввод приходит на хост после соответствующего такта, хост восстанавливает сохранённое состояние и повторяет затронутые шаги с этим вводом. Окно отката ограничено 24 тактами (400 мс); более старый ввод не меняет уже рассчитанный результат. После потери отдельного UDP-пакета недавний ввод повторяется в следующих пакетах.
- Правила движения и нормализованная геометрия поля заданы в `src/LanPong/GameConstants.cs`; браузер повторяет нужные значения в `frontend/src/motion.ts` для прогноза и рисования.
- Браузер получает текущее состояние своего процесса примерно 60 раз в секунду и рисует его через `requestAnimationFrame`. Между сообщениями он кратко продолжает движение мяча, останавливая прогноз у вероятного столкновения; небольшие исправления траектории сглаживаются. Своя ракетка откликается сразу на ввод. После гола, нового матча или переподключения история движения очищается. Из-за прогноза результат столкновения или счёт может быть кратко исправлен после прихода сетевого ввода.
- Сервер записывает последние 12 игровых событий с ID, номером такта и координатами. Хост передаёт их гостю в авторитетном UDP-состоянии, а оба процесса включают их в снимки WebSocket. Браузер воспроизводит подтверждённое событие один раз по его ID, даже если история приходит повторно или хост пересчитывает прошлые такты. След мяча и визуальная подсветка дополняют звуковой отклик.
- Статичный фон игрового поля кэшируется и обновляется при изменении размера Canvas.
- Строка **«Пинг»** показывает сглаженное время запроса и ответа между двумя игровыми процессами по UDP. Измерение обновляется примерно раз в секунду и становится пустым при потере соединения.
- После нажатия «Подключиться» запрос вызова повторяется до ответа. Если ответа нет 10 секунд, подключение завершается. Ожидающий вызов истекает через 2 минуты или после 5 секунд без пакетов от соперника. Если уже установленная связь пропала на 5 секунд, гостевая сессия завершается и для новой игры нужен повторный вход вручную. Запрос нового матча от второго игрока повторяется до получения нового состояния. Пакеты вызова проверяются по ID и адресу, а игровые пакеты — по адресу и идентификатору сеанса; ввод привязан к номеру матча и такту. Состояния хоста принимаются по возрастающему номеру такта.

Формат WebSocket версии 3 — массивы MessagePack с фиксированными позициями. Снимок содержит 21 элемент:

```text
[3, role, connection, message, udpPort, localAddresses, peerAddress,
 leftY, rightY, ballX, ballY, ballVx, ballVy, leftScore, rightScore,
 phase, countdown, tick, roundId, pingMs, recentEvents]
```

`recentEvents` — массив последних событий вида `[id, kind, tick, x, y]`. `id` — строка, `tick` — номер такта, `x` и `y` — нормализованные координаты поля от 0 до 1. Значения `kind`: `1` подача, `2` удар ракетки, `3` удар стены, `4` гол, `5` начало матча. Команда управления — `[3, axis]`, где `axis` равен `-1`, `0` или `1`. Числовые значения enum: `role` — `0` нет роли, `1` хост, `2` гость; `connection` — `0` ожидание действий, `1` ожидание игрока, `2` подключение, `3` подключено, `4` входящий вызов, `5` ожидание принятия; `phase` — `0` ожидание, `1` отсчёт, `2` игра, `3` завершение. Начальное число `3` — версия браузерного протокола, которая не связана с версией UDP.

Игра предназначена для доверенной локальной сети. Решение `LanPong.slnx` находится в корне, C# приложение — в `src/LanPong`, исходники фронтенда — в `frontend`, а тесты — в `tests`. Общие настройки сборки заданы в `Directory.Build.props`. Версии NuGet-пакетов находятся в `Directory.Packages.props`.

## Тесты

Сначала выполните `pnpm install --frozen-lockfile`. Затем из корня проекта:

```bash
dotnet test --solution LanPong.slnx -c Release
pnpm typecheck
pnpm test:frontend
python3 tests/integration/integration_test.py
```

Первая команда запускает TUnit тесты столкновений, переходов между раундами, начисления очков, игровых событий, восстановления состояния и отката после позднего ввода через `Microsoft.Testing.Platform`, выбранную в `global.json`. Имена C# тестов следуют [формату](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) `Метод_WhenУсловие_ОжидаемыйРезультат`. Вторая проверяет типы TypeScript. Третья проверяет отображение текущего состояния, исправление траектории, локальный прогноз ракетки, отклик на события и кэш Canvas без браузера. Для четвёртой нужен Python 3; она собирает фронтенд и приложение, затем запускает две локальные копии для проверки IPv4 и, если доступен IPv6 loopback, IPv6 UDP, WebSocket, передачи игровых событий, пинга, прогноза гостя при задержанных пакетах состояния, синхронизации, повторного матча и корректного завершения обоих игроков по SIGTERM. Проверка сети открывает локальные TCP-порты 5180 и 5181, UDP-порт 47888 и свободный локальный UDP-порт реле.

Для отдельной проверки mDNS на одном компьютере запустите `LANPONG_REQUIRE_MDNS_LOOPBACK=1 python3 tests/integration/integration_test.py`. Она ищет игру через mDNS и проверяет снятие и повторное объявление службы. Совместное использование UDP-порта 5353 несколькими процессами на одной машине зависит от ОС, поэтому обычный интеграционный тест оставляет эту проверку выключенной.

Обоснование оптимизаций, источники и ограничения описаны в [RESEARCH.md](RESEARCH.md).
