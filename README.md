# LAN Pong

Pong против простого бота на одном компьютере или для двух игроков в одной локальной сети. В игре с ботом человек управляет левой ракеткой, а приложение — правой. Для игры по сети каждый игрок запускает приложение на своём компьютере и открывает локальную страницу в браузере. Компьютеры обмениваются игровыми пакетами напрямую через UDP; отдельный игровой сервер не нужен.

## Требования

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0) на машине разработки или сборки.
- Node.js **20.19+** в ветке 20 или **22.12+** и pnpm **11.15.1** для разработки и публикации фронтенда.
- Для игры с другом оба компьютера должны быть в одной локальной сети. Игровой UDP-порт выбирает ОС; входящий трафик на нём должен быть доступен на компьютере, который ожидает соперника. Для автоматического поиска сеть должна пропускать локальный mDNS-трафик на UDP-порту **5353**. Для игры с ботом сеть не требуется.
- Современный браузер с поддержкой Canvas и WebSocket.

Игра использует .NET 10 и C# 14. UDP-пакеты и обмен с браузером через WebSocket используют MessagePack; HTTP API остаётся на JSON. C# тесты используют [TUnit](https://tunit.dev/docs/getting-started/installation/). Версии NuGet-пакетов заданы централизованно.

## Разработка фронтенда

Один раз установите зависимости из корня проекта:

```bash
pnpm install --frozen-lockfile
```

Запустите два процесса в отдельных терминалах:

```bash
# Терминал 1: API и WebSocket
dotnet run --project src/LanPong/LanPong.csproj --launch-profile Development

# Терминал 2: Vite
pnpm dev
```

Откройте `http://127.0.0.1:5173`. Vite обновляет страницу при изменении файлов в `frontend/` и пересылает запросы `/api` и `/ws` приложению .NET на `http://127.0.0.1:5080`. Если .NET запущен на другом адресе, задайте `LANPONG_DOTNET_URL` перед `pnpm dev`. В этом режиме браузер открывает адрес Vite.

Исходники страницы находятся в `frontend/index.html` и `frontend/src/`. Код приложения написан на TypeScript; Vite преобразует его для браузера в режиме разработки и при сборке. Команда `pnpm typecheck` проверяет типы отдельно, а `pnpm build` проверяет их перед сборкой и создаёт готовые файлы в `src/LanPong/wwwroot`; эту папку генерирует Vite, и она не хранится в Git. Для форматирования используйте `pnpm format`, для проверки формата — `pnpm format:check`.

`frontend/src/game.ts` соединяет модули страницы: `snapshot.ts` разбирает HTTP-состояние, `wsProtocol.ts` — бинарный WebSocket, `session.ts` принимает снимки и проверяет их порядок, `motion.ts` рассчитывает отображаемое движение, `arena.ts` рисует Canvas, `feedback.ts` и `sound.ts` показывают и озвучивают события, `view.ts` обновляет интерфейс, а `input.ts` собирает управление. Стили разделены по областям страницы в `frontend/src/styles/` и подключаются через `style.css` в прежнем порядке.

## Сборка из исходников и публикация

Для запуска из исходников после установки зависимостей соберите статические файлы:

```bash
pnpm build
```

После этого `dotnet run` обслуживает страницу из `src/LanPong/wwwroot`. При изменении фронтенда повторите `pnpm build`. Для публикации приложения вместе со статическими файлами:

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -o .artifacts/publish
```

`dotnet publish` сам выполняет `pnpm install --frozen-lockfile` и `pnpm build`, поэтому в публикацию попадают свежие файлы из `wwwroot`. По умолчанию он создаёт нативное self-contained приложение для ОС и архитектуры машины сборки. При необходимости укажите целевую архитектуру через `-r`, например `-r osx-arm64`; для другой ОС AOT-публикацию нужно выполнять на соответствующей ОС. Для запуска опубликованного приложения .NET SDK, Node.js и pnpm не нужны.

### Проверка ONNX Runtime в Native AOT

Диагностическая команда `--onnx-smoke` загружает включённую в публикацию модель `Models/aot-smoke.onnx`, выполняет float32-вычисление `2 + 1` через ONNX Runtime CPU и завершается с ошибкой, если результат не равен `3`. Модель воспроизводится без дополнительных Python-пакетов командой `python3 tools/generate_onnx_smoke_model.py`; параметр `--check` сравнивает файл с генератором.

```bash
dotnet publish src/LanPong/LanPong.csproj -c Release -r osx-arm64 -o .artifacts/publish/osx-arm64
LANPONG_TEST_BINARY="$PWD/.artifacts/publish/osx-arm64/LanPong" python3 tests/integration/published_smoke_test.py
```

Вторая команда проверяет наличие модели и нативной библиотеки ONNX Runtime в каталоге публикации, запускает нативный исполняемый файл с `--onnx-smoke`, затем проверяет обычный запуск страницы и `/api/status`. Workflow выпуска выполняет ту же проверку после публикации для `osx-arm64`, `linux-x64` и `win-x64`; на macOS и Linux он также запускает полный интеграционный сценарий против опубликованного файла.

Проверено 7 октября 2026 года на macOS 27.0 ARM64 с .NET SDK 10.0.400 и `Microsoft.ML.OnnxRuntime` 1.30.0: Native AOT публикация, вычисление `2 → 3`, запуск HTTP и полный интеграционный тест прошли. Файл `LanPong` занимает **18 562 440 байт**, `libonnxruntime.dylib` — **43 879 424 байта**; весь каталог — **156 184 861 байт** (с отладочным `LanPong.dSYM`), архив `tar.gz` по схеме выпуска — **37 064 330 байт**. Модель занимает **115 байт**, SHA-256: `4e6e278a2e3cdc6d837447daec450e4fce1a2da4ffae34ed005db2a8c3784aeb`. В успешном логе публикации отмечены `IL3053` (AOT) и `IL2104` (trimming) для `MessagePack`; предупреждений по ONNX Runtime не было. NuGet-пакет также добавил в macOS-публикацию неиспользуемые Windows DLL, включая `onnxruntime.dll` размером **16 728 888 байт**.

## Выпуски на GitHub

При push тега `v*` GitHub Actions сначала запускает тесты, затем публикует Native AOT приложение на macOS ARM64, Windows x64 и Linux x64. После проверки опубликованных приложений workflow создаёт GitHub Release и прикрепляет `LanPong-osx-arm64.tar.gz`, `LanPong-win-x64.zip` и `LanPong-linux-x64.tar.gz`. Каждый архив содержит весь каталог публикации, включая страницу игры. Например, для выпуска `v1.0.0`:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Теги с суффиксом вроде `v1.0.0-rc.1` создают предварительный релиз. Публикация релиза вручную также запускает сборку и добавляет недостающие архивы. Если в репозитории включены неизменяемые релизы GitHub, используйте выпуск через push тега: архивы прикрепляются при создании релиза, до его публикации. Повторный запуск пропускает релиз, когда все три архива уже прикреплены. Linux-сборка создаётся на Ubuntu 24.04 и требует совместимой версии системных библиотек; macOS-сборка не подписана сертификатом Apple.

## Игра против бота на одном компьютере

Запустите приложение и откройте его страницу в браузере на том же компьютере. Введите ник и выберите **«Играть · Simple»** или **«Играть · Hard»**. Simple следует за мячом с ограниченной частотой реакции; Hard использует обученную ONNX-модель. Матч начнётся после отсчёта: вы управляете левой ракеткой клавишами **W/S** или **↑/↓**, либо экранными кнопками на сенсорном устройстве. Бот управляет правой ракеткой; игра идёт до **7 очков**. Подключение к другому компьютеру и UDP-порт не нужны.

Если модель Hard не загружается или даёт ошибку, игра продолжается против Simple, а страница постоянно показывает уведомление о замене. После завершения матча нажмите кнопку реванша, чтобы сыграть ещё раз. **«К выбору игры»** возвращает к выбору соперника; затем можно запустить новую игру с ботом или выбрать **«Быстрая игра»** либо **«Присоединиться»** для игры по сети. Во время игры с ботом адреса для подключения и сетевой пинг не показываются.

Схема наблюдений обучаемого бота, генератор данных и проверка Teacher против Simple описаны в [BOT_TRAINING_DATA.md](docs/bots/BOT_TRAINING_DATA.md). Обучение и экспорт ONNX описаны в [BOT_MODEL.md](docs/bots/BOT_MODEL.md). Встраивание модели, проверка опубликованной сборки и результаты Hard описаны в [BOT_HARD_RUNTIME.md](docs/bots/BOT_HARD_RUNTIME.md).

## Запуск на двух компьютерах

Скачайте и распакуйте архив своей платформы из GitHub Releases или скопируйте содержимое `.artifacts/publish` на компьютеры с подходящей ОС и архитектурой. В папке с опубликованным приложением запустите его на **каждом** компьютере:

```bash
./LanPong --urls http://127.0.0.1:5080
```

В Windows запустите `LanPong.exe` с тем же параметром. Для запуска из исходников на каждом компьютере по-прежнему можно выполнить `pnpm install --frozen-lockfile`, `pnpm build` и `dotnet run --project src/LanPong/LanPong.csproj -c Release`.

Откройте адрес `http://127.0.0.1:5080` **на том же компьютере**, где запущена команда.

Локальная страница по умолчанию слушает `127.0.0.1`; это не ограничивает IPv6-соединение между игровыми процессами. Если страницу нужно открывать по IPv6, настройте привязку ASP.NET Core к `::1` или нужному IPv6-адресу.

1. Каждый игрок вводит свой ник. Он сохраняется в браузере для следующих партий.
2. Каждый нажимает **«Быстрая игра»**. Приложение ищет ожидающие игры в локальной сети и выбирает случайную. Если никого нет, оно само открывает игру на свободном UDP-порту и ждёт соперника. Матч начинается автоматически после подключения второго игрока.
3. Чтобы подключиться к конкретному другу, откройте **«Присоединиться»**: найдите его игру по нику или введите адрес и порт вручную. На ожидающем устройстве адрес и выбранный порт находятся в разделе ручного подключения.
4. Управление ракеткой: **W/S** или **↑/↓**. На сенсорном экране есть экранные кнопки. Игра идёт до **7 очков**.

Если один из игроков покидает быструю игру, матч и временное лобби закрываются у обоих. Для новой партии снова нажмите **«Быстрая игра»** или подключитесь к другу вручную. Если сообщение о выходе не дошло по UDP, второй игрок выйдет после 5 секунд без связи.

Входящий вызов сопровождается коротким звуковым сигналом для первого игрока. Удары ракетки и стен, подача и гол сопровождаются звуками и короткими эффектами на поле. После гола подсвечивается счёт забившей стороны. Звук можно выключить или настроить ползунком громкости; настройка сохраняется в браузере. Браузер включает воспроизведение звука после первого действия игрока.

Адреса `127.0.0.1` и `::1` подходят только для проверки двух копий на одном компьютере. Для игры по сети второму игроку нужен адрес первого компьютера из списка в приложении: IPv4, например `192.168.x.x`, или IPv6. Адрес IPv6 вводится в поле без квадратных скобок. Если используется link-local IPv6 (`fe80::…`), второму игроку нужна зона **его собственного** сетевого интерфейса, например `%en0` или `%3`; зона из списка адресов первого компьютера может отличаться. Автоматический поиск mDNS подставляет зону принимающего интерфейса сам.

Автоматический поиск использует DNS-SD через mDNS по IPv4 (`224.0.0.251`) и IPv6 (`ff02::fb`) и получает назначенный приложением игровой UDP-порт из объявления. Он работает в пределах локального сетевого сегмента: изоляция клиентов Wi-Fi, настройки маршрутизатора или брандмауэра могут блокировать multicast. Если игра не появляется в списке, подключитесь по IP и порту вручную. Если подключение по IP тоже не происходит, проверьте доступность компьютеров и входящий UDP на игровом порту первого компьютера.

Для завершения приложения нажмите **Ctrl+C** в его терминале. Процесс сообщает сопернику о выходе, закрывает локальные WebSocket-соединения и освобождает UDP-порт. При принудительном завершении процесса без обработки сигнала соперник обнаружит потерю связи по обычному тайм-ауту.

## Проверка на одном компьютере

Сначала выполните `pnpm install --frozen-lockfile` и `pnpm build`. Затем откройте два терминала в папке проекта:

```bash
# Первый терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release

# Второй терминал
dotnet run --project src/LanPong/LanPong.csproj -c Release --launch-profile Player2
```

Откройте `http://127.0.0.1:5080` и `http://127.0.0.1:5081` в двух окнах браузера. Нажмите **«Быстрая игра»** в обоих окнах. Для проверки ручного подключения нажмите её только в первом окне, раскройте адрес и порт, затем введите их во втором окне на вкладке **«Присоединиться»**.

## Как устроена сеть

- Пока игрок ждёт подключения, его процесс объявляет службу `_lanpong._udp.local.` через DNS-SD/mDNS по IPv4 и IPv6. Запись SRV сообщает выбранный ОС игровой UDP-порт, записи A и AAAA — адреса, а TXT — версию протокола и ник хоста. Кнопка **«Быстрая игра»** запускает поиск через локальный backend: из найденных игр случайно выбирается одна, а при отсутствии свободных игр устройство начинает ожидать соперника. Если два игрока начинают поиск одновременно, идентификатор экземпляра mDNS определяет, кто оставит открытую игру, а кто присоединится к ней. Для выбора конкретного игрока браузер вызывает `/api/discover` и показывает ники найденных игр. При подключении гость отправляет UDP `Hello` с ID вызова и своим ником. Игра, запущенная через **«Быстрая игра»**, принимает вызов автоматически; mDNS не передаёт игровые данные. Схему mDNS и DNS-SD определяют [RFC 6762](https://www.rfc-editor.org/rfc/rfc6762) и [RFC 6763](https://www.rfc-editor.org/rfc/rfc6763).
- Локальная страница общается со своим процессом C# через WebSocket на `127.0.0.1`. Снимки состояния и команды управления передаются бинарными сообщениями MessagePack версии 7. HTTP-запросы `/api` сохраняют JSON и строковые значения роли, соединения, фазы и режима соперника; снимки содержат `version: 7`. Для локального матча браузер отправляет `POST /api/local-opponent` с ником и режимом `simple` или `hard`; отсутствие режима по-прежнему выбирает Simple. Тот же процесс рассчитывает обе ракетки без игрового UDP-соединения. Профили `Player1` и `Player2` в `src/LanPong/Properties/launchSettings.json` запускают собранную страницу на портах 5080 и 5081. Первый профиль выбирается при обычном `dotnet run`; второй можно выбрать в Rider или параметром `--launch-profile Player2`. Профиль `Development` запускает API и WebSocket для Vite на порту 5080.
- Ожидающий игрок слушает назначенный ОС UDP-порт по IPv4 и IPv6, второй использует свободный локальный порт и выбранное семейство адресов. Между ними идёт прямой обмен бинарными пакетами MessagePack версии 8. Идентификаторы вызова, сеанса и перезапуска передаются как 16-байтные `Guid` через `NativeGuidResolver`; пустые идентификаторы отклоняются. Числовой тег `Union` определяет тип сообщения; фаза игры передаётся числовым значением enum. Для игры обе копии приложения должны использовать одинаковую версию UDP-протокола. Версии UDP и браузерного WebSocket независимы.
- Оба процесса рассчитывают физику с фиксированным шагом 1/60 с. Хост остаётся авторитетным и отправляет полное состояние примерно 30 раз в секунду. Гость прогнозирует игру между этими состояниями и повторно рассчитывает шаги после получения очередного состояния хоста.
- Гость отправляет для каждого шага номер такта и несколько последних направлений ракетки. Если ввод приходит на хост после соответствующего такта, хост восстанавливает сохранённое состояние и повторяет затронутые шаги с этим вводом. Окно отката ограничено 24 тактами (400 мс); более старый ввод не меняет уже рассчитанный результат. После потери отдельного UDP-пакета недавний ввод повторяется в следующих пакетах.
- Правила движения и нормализованная геометрия поля заданы в `src/LanPong/GameConstants.cs`; браузер повторяет нужные значения в `frontend/src/motion.ts` для прогноза и рисования.
- Браузер получает текущее состояние своего процесса примерно 60 раз в секунду и рисует его через `requestAnimationFrame`. Между сообщениями он кратко продолжает движение мяча, останавливая прогноз у вероятного столкновения; небольшие исправления траектории сглаживаются. Своя ракетка откликается сразу на ввод, а исправления позиций ракеток после отката плавно отображаются в течение 80 мс без изменения игровой симуляции. После гола, нового матча или переподключения история движения очищается. Из-за прогноза результат столкновения или счёт может быть кратко исправлен после прихода сетевого ввода.
- Сервер записывает последние 12 игровых событий с ID, номером такта и координатами. Хост передаёт их гостю в авторитетном UDP-состоянии, а оба процесса включают их в снимки WebSocket. Браузер воспроизводит подтверждённое событие один раз по его ID, даже если история приходит повторно или хост пересчитывает прошлые такты. След мяча и визуальная подсветка дополняют звуковой отклик.
- Статичный фон игрового поля кэшируется и обновляется при изменении размера Canvas.
- Строка **«Пинг»** показывает сглаженное время запроса и ответа между двумя игровыми процессами по UDP. Измерение обновляется примерно раз в секунду и становится пустым при потере соединения.
- После нажатия «Подключиться» запрос вызова повторяется до ответа. Если ответа нет 10 секунд, подключение завершается. Ожидающий вызов истекает через 2 минуты или после 5 секунд без пакетов от соперника. Если уже установленная связь пропала на 5 секунд, гостевая сессия завершается и для новой игры нужен повторный вход вручную. Запрос нового матча от второго игрока повторяется до получения нового состояния. Пакеты вызова проверяются по ID и адресу, а игровые пакеты — по адресу и идентификатору сеанса; ввод привязан к номеру матча и такту. Состояния хоста принимаются по возрастающему номеру такта.

Формат WebSocket версии 7 — массивы MessagePack с фиксированными позициями. Снимок содержит 26 элементов:

```text
[7, role, connection, message, udpPort, localAddresses, peerAddress,
 leftY, rightY, ballX, ballY, ballVx, ballVy, leftScore, rightScore,
 phase, countdown, tick, roundId, pingMs, recentEvents, localNickname, peerNickname,
 opponentMode, requestedOpponentMode, opponentFallbackActive]
```

`recentEvents` — массив последних событий вида `[id, kind, tick, x, y]`. `id` — строка, `tick` — номер такта, `x` и `y` — нормализованные координаты поля от 0 до 1. Значения `kind`: `1` подача, `2` удар ракетки, `3` удар стены, `4` гол, `5` начало матча. Команда управления — `[7, axis]`, где `axis` равен `-1`, `0` или `1`. Числовые значения enum: `role` — `0` нет роли, `1` хост, `2` гость; `connection` — `0` ожидание действий, `1` ожидание игрока, `2` подключение, `3` подключено, `4` входящий вызов, `5` ожидание принятия, `6` поиск соперника; `phase` — `0` ожидание, `1` отсчёт, `2` игра, `3` завершение; режимы соперника — `0` нет соперника, `1` игра по сети, `2` Simple, `3` Hard. `opponentMode` обозначает действующего бота, `requestedOpponentMode` — выбор игрока, а `opponentFallbackActive` сообщает о переходе с Hard на Simple. В HTTP API режимы передаются строками `none`, `lan`, `simple`, `hard`. Начальное число `7` — версия браузерного протокола, независимая от версии UDP.

Игра предназначена для доверенной локальной сети. Решение `LanPong.slnx` находится в корне, C# приложение — в `src/LanPong`, исходники фронтенда — в `frontend`, а тесты — в `tests`. Общие настройки сборки заданы в `Directory.Build.props`. Версии NuGet-пакетов находятся в `Directory.Packages.props`.

## Тесты

Сначала выполните `pnpm install --frozen-lockfile`. Затем из корня проекта:

```bash
dotnet test --solution LanPong.slnx -c Release
pnpm typecheck
pnpm test:frontend
python3 tests/integration/integration_test.py
```

Первая команда запускает TUnit тесты столкновений, переходов между раундами, начисления очков, игровых событий, восстановления состояния и отката после позднего ввода через `Microsoft.Testing.Platform`, выбранную в `global.json`. Имена C# тестов следуют [формату](https://learn.microsoft.com/dotnet/core/testing/unit-testing-best-practices#follow-test-naming-standards) `Метод_WhenУсловие_ОжидаемыйРезультат`. Вторая проверяет типы TypeScript. Третья проверяет отображение текущего состояния, исправление траектории, локальный прогноз ракетки, отклик на события и кэш Canvas без браузера. Для четвёртой нужен Python 3; она собирает фронтенд и приложение, затем запускает локальные Simple и Hard с реваншем, выходом и проверкой замены недоступной модели, а также две локальные копии для проверки IPv4 и, если доступен IPv6 loopback, IPv6 UDP, WebSocket, передачи игровых событий, пинга, прогноза гостя при задержанных пакетах состояния, синхронизации, повторного матча, автоматического выбора UDP-порта и принятия вызова в быстрой игре, отмены поиска и корректного завершения обоих игроков по SIGTERM. Проверка сети открывает локальные TCP-порты 5180 и 5181, UDP-порт 47888 для проверки ручного API, а также свободные UDP-порты для быстрой игры и реле.

Для отдельной проверки mDNS на одном компьютере запустите `LANPONG_REQUIRE_MDNS_LOOPBACK=1 python3 tests/integration/integration_test.py`. Она ищет игру через mDNS, проверяет снятие и повторное объявление службы, подключение к доступной быстрой игре и одновременный запуск поиска двумя игроками. Совместное использование UDP-порта 5353 несколькими процессами на одной машине зависит от ОС, поэтому обычный интеграционный тест оставляет эту проверку выключенной.

Чтобы прогнать тот же интеграционный сценарий против опубликованного Native AOT приложения на macOS или Linux, укажите путь к исполняемому файлу в `LANPONG_TEST_BINARY`; повторная сборка при этом не выполняется:

```bash
LANPONG_TEST_BINARY=/path/to/LanPong python3 tests/integration/integration_test.py
```
