# Настройка каталога ботов

Каталог задаётся в секции `Bots` файла `appsettings.json` и обычных источниках конфигурации ASP.NET Core. В поставке есть `lada` и `iskra` со стратегией `tracker`, а также `vektor` со стратегией `onnx`. Дополнительный профиль этих стратегий требует только конфигурации: сервер и браузер обнаруживают его по ID. Новая стратегия поведения требует реализации и регистрации дескриптора и `IBotStrategyFactory` в коде, а при новом виде настроек — расширения типизированной конфигурации и её проверки.

Это руководство описывает текущий контракт. Запуск игры и LAN-сценарии находятся в [README](../../README.md), решения — в [research.md](research.md), этапы и проверенная область — в [plan.md](plan.md), метод и ограничения измерений — в [performance.md](performance.md). Точные правила реализованы в [BotsOptionsValidator.cs](../../src/LanPong/BotsOptionsValidator.cs).

## Добавить четвёртого бота

Добавьте следующий **полный объект** четвёртым элементом `Bots.Entries` в действующем `appsettings.json`, сохранив первые три элемента. Это профиль `sokol`, а не отдельный файл конфигурации и не замена всего массива.

```json
{
  "Id": "sokol",
  "Name": "Сокол",
  "Description": "Раньше замечает приближение мяча и поправляет позицию в спокойном ритме. Подходит для тренировки длинных розыгрышей.",
  "Style": "Ранняя реакция, умеренный прогноз",
  "Difficulty": "Средний",
  "Category": "Тренировка",
  "Order": 40,
  "Glyph": "▲",
  "Enabled": true,
  "StrategyId": "tracker",
  "Tracker": {
    "ObservationIntervalTicks": 7,
    "ObservationActivationX": 0.6,
    "LookAheadSeconds": 0.35,
    "TargetDeadZone": 0.02
  },
  "FallbackBotId": null
}
```

Для выбора этого профиля по умолчанию измените свойство `DefaultBotId` внутри секции `Bots` на `"sokol"`. Затем полностью остановите и снова запустите процесс. `DefaultBotId` должен указывать на существующего включённого бота. Он задаёт предпочтение при начальном выборе в браузере и выбор диагностики без явного ID. В открытой вкладке предыдущий выбор сохраняется, пока тот допускает игру; иначе браузер выбирает доступный default, затем первого подходящего бота. Сам по себе default не запускает матч и не заменяет обязательный `botId` в HTTP-запросе.

В примерах ниже текущая папка — каталог опубликованного приложения с исполняемым файлом, изменённым `appsettings.json`, статическими файлами и `Models`. Другой абсолютный `--contentRoot` меняет также обычное расположение `wwwroot`: новый корень должен содержать опубликованную страницу и её файлы либо приложение должно явно использовать абсолютный web root. Чтобы перенести только модель, оставьте content root публикации и задайте абсолютный `ModelPath`. Явное `--environment Production` исключает загрузку случайного файла настроек другого окружения, включая окружение, заданное через `DOTNET_ENVIRONMENT`.

```sh
./LanPong --environment Production --contentRoot "$PWD" --urls http://127.0.0.1:5080
```

На Windows имя исполняемого файла — `LanPong.exe`. Публикация и фактически проверенные платформы описаны в README и плане.

## Поля каталога и их ограничения

Все записи проверяются при запуске, в том числе отключённые. Неизвестные свойства, неверные типы и нарушения ограничений отвергаются с указанием конфигурационного пути. Каталог должен содержать хотя бы одну запись. ID должны быть уникальны.

Длины текстов измеряются в **единицах UTF-16**, как `.NET string.Length` и JavaScript `string.length`: большинство букв занимает одну единицу, символ вне BMP, например многие эмодзи, — две. Обязательный текст не может быть пустым или состоять только из пробельных символов. Непустые значения сохраняются без обрезки и нормализации. Это отдельные правила от проверки человеческого ника.

| Поле               | Значение и проверка                                                                                                                                                                                                                            |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Id`               | Стабильный ID, 1–64 ASCII-символа: начинается с `a`–`z`, далее строчные буквы, цифры и одиночные дефисы между непустыми частями. Примеры: `sokol`, `steady-tracker`. Пробелы, заглавные буквы, начальный/конечный и повторный дефис запрещены. |
| `Name`             | Отображаемое имя, обязательный текст до 64 единиц UTF-16.                                                                                                                                                                                      |
| `Description`      | Описание профиля, обязательный текст до 512.                                                                                                                                                                                                   |
| `Style`            | Краткое объяснение поведения, обязательный текст до 128.                                                                                                                                                                                       |
| `Difficulty`       | Подсказка сложности, обязательный текст до 64. Это операторская подпись, а не автоматически измеренный рейтинг.                                                                                                                                |
| `Category`         | Название группы, обязательный текст до 64. Совпадающие строки образуют одну группу; различия регистра создают разные группы.                                                                                                                   |
| `Order`            | Целое число `Int32` от 0 до 2 147 483 647; при отсутствии — 0.                                                                                                                                                                                 |
| `Glyph`            | Необязательный знак: `null`/отсутствует либо непробельный текст до 16. При отсутствии браузер показывает инициалы имени.                                                                                                                       |
| `Enabled`          | Логическое значение, по умолчанию `true`. Отключённый бот остаётся в каталоге, но не допускает выбор и не может быть default или целью fallback.                                                                                               |
| `StrategyId`       | Зарегистрированная стратегия. Сейчас `tracker` или `onnx`; синтаксис ID такой же, как у `Id`.                                                                                                                                                  |
| `Tracker` / `Onnx` | Для `tracker` обязателен объект `Tracker` и запрещён `Onnx`; для `onnx` — наоборот.                                                                                                                                                            |
| `FallbackBotId`    | `null`/отсутствует либо ID существующего включённого бота. Синтаксис и регистр такие же, как у `Id`; пустая строка не означает отсутствие резерва.                                                                                             |

Имена и прочие метаданные выводятся как текст. HTML в них не становится разметкой, а `Glyph` не является URL изображения. Меняйте `Name` и подписи без изменения стабильного `Id`, если клиентские ссылки на профиль должны продолжать работать.

API сортирует записи по `Order`, затем по `Id` в ordinal-порядке. Браузер объединяет их по `Category`: порядок групп определяется первой записью группы в отсортированном каталоге, порядок карточек внутри группы сохраняется. Индекс записи в JSON и её место после этой сортировки — разные вещи.

## Параметры поведения

Игровая симуляция работает с частотой 60 тиков в секунду. Каденция задаётся целым числом тиков; 7 тиков — примерно 117 мс. Числа с плавающей точкой должны быть конечными: `NaN` и бесконечности недопустимы.

| Поле `Tracker`             | Допустимое значение                                                                                 | Значение при пропуске |
| -------------------------- | --------------------------------------------------------------------------------------------------- | --------------------- |
| `ObservationIntervalTicks` | Целое 1–600                                                                                         | 9                     |
| `ObservationActivationX`   | От 0 включительно до плоскости контакта правой ракетки `RightContactX` исключительно, около 0.93925 | 0.72                  |
| `LookAheadSeconds`         | От 0 до 2 секунд включительно                                                                       | 0.25                  |
| `TargetDeadZone`           | От 0 до 0.5 включительно, в нормализованной вертикальной координате                                 | 0.018                 |

Трекер наблюдает приближающийся к правой ракетке мяч после порога X, прогнозирует его положение на коротком горизонте и двигается, когда расстояние до цели превышает dead zone. Период наблюдения ограничивает частоту пересчёта цели. Параметры и изменяемое состояние отдельны для каждого профиля и матча; одинаковый `StrategyId` не объединяет их состояние.

| Поле `Onnx`             | Допустимое значение                                                                                | Значение при пропуске                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `ModelPath`             | Непробельный путь без NUL; абсолютный либо относительно content root приложения                    | `Models/hard-v1.onnx`                                              |
| `ExpectedSha256`        | Ровно 64 шестнадцатеричных символа, без префикса; любой регистр принимается и приводится к нижнему | `5d5d3cf0910d967cf2d6dc60e8fe0b63f772060178bf6673f6ddc5cdba98ab5a` |
| `InferenceCadenceTicks` | Целое 1–600                                                                                        | 9                                                                  |

Путь определяется content root, а не автоматически папкой исполняемого файла. Обычные `--contentRoot`, `ASPNETCORE_CONTENTROOT` и настройки окружения используются и приложением, и конфигурационной диагностикой. Отдельный файл `appsettings.Production.json` или переменная окружения может переопределить значения базового файла.

Наличие модели, её SHA-256, схема и native runtime проверяются при подготовке выбранного профиля, а не при чтении каталога. Совпадающий SHA-256 не делает произвольную ONNX-модель совместимой: требуется ровно один вход `observation` float32 `[1,10]` и один выход `logits` float32 `[1,3]`, с конечными значениями при прогреве и выводе. Порядок классов: вверх, стоять, вниз; если «стоять» делит максимальный logit, выбирается «стоять». Во время игры ONNX пересчитывает действие на тиках, кратных `InferenceCadenceTicks`, и удерживает его между ними. Хеш и модель выбирайте согласованно; замена файла модели уже работающему процессу не обновляет подготовленную сессию.

## Источники конфигурации и перезапуск

Каталог связывается, проверяется и копируется один раз при старте. Изменение файла, переменной окружения или сигнал reload не меняет действующий каталог, параметры, имена, текущий матч или известную доступность. После правки конфигурации либо исправления модели нужен **перезапуск процесса**. После перезапуска обновите страницу браузера, чтобы заново получить каталог.

Стандартные источники конфигурации объединяют `Entries` по **числовому индексу**, а не по `Id` и не заменяют массив целиком. У исходного файла индексы 0, 1, 2 соответствуют `lada`, `iskra`, `vektor`; добавленный выше `sokol` имеет индекс 3. Более короткий массив в файле окружения может оставить хвост базового массива. Частичная запись с другим `Id` наследует остальные поля того же индекса. При смене `onnx` на `tracker` у индекса 2 унаследованный объект `Onnx` не исчезнет и нарушит проверку взаимного исключения настроек.

Для изменения состава или типа стратегии редактируйте полный базовый документ, удаляйте старый объект настроек и проверяйте остальные активные источники. Для точечного изменения уже существующего профиля можно применять обычные ключи. Двойной underscore в переменной окружения соответствует двоеточию конфигурационного пути:

```sh
Bots__DefaultBotId=sokol \
Bots__Entries__3__Tracker__ObservationIntervalTicks=7 \
./LanPong --environment Production --contentRoot "$PWD" --urls http://127.0.0.1:5080
```

Этот пример предполагает, что полный объект `sokol` уже добавлен в JSON. Установка только одного поля нового индекса не создаёт корректный профиль с обязательными метаданными. После перестановки элементов исходного массива обновите адресованные по индексу overrides. На командной строке аналогичный путь — `--Bots:Entries:3:Tracker:ObservationIntervalTicks 7`.

## Доступность и явный резерв

`GET /api/bots` возвращает `version: 8`, `defaultBotId` и массив `bots`. Каждая публичная запись содержит `id`, `name`, `description`, `style`, `difficulty`, `category`, `order`, `glyph`, `enabled`, `fallbackBotId`, `availability`, `availabilityReason`, `canPlay`. В ответе нет `StrategyId`, путей модели, хешей и объектов настроек.

| `availability` | Значение                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ready`        | Трекер либо уже успешно подготовленный профиль модели.                                                                                                 |
| `notChecked`   | Модель ещё не проверялась. Её можно попытаться запустить; успешный запуск не гарантирован.                                                             |
| `unavailable`  | Процесс уже обнаружил ошибку подготовки или исполнения. Причина безопасная и пользовательская; исходные пути и native-ошибки не передаются в каталоге. |
| `disabled`     | Запись имеет `Enabled: false`; `canPlay` равен `false`.                                                                                                |

Известная ошибка остаётся зафиксированной до перезапуска, включая последующие выборы и реванши. `canPlay` означает допустимость **попытки выбора**: включённая запись либо одно из звеньев её явной цепочки ещё имеет состояние `ready` или `notChecked`. Поэтому `unavailable` с доступным резервом может иметь `canPlay: true`; unchecked-резерв тоже может отказать при подготовке.

`FallbackBotId` задаёт единственную следующую запись цепочки. Цель обязана существовать и быть включённой; ссылка на себя и любые циклы отвергаются при старте, в том числе в отключённых исходных записях. Резерв может использовать любую из зарегистрированных стратегий. Например, `vektor` в поставке явно ссылается на `lada`.

Перед допуском матча подготавливаются доступные звенья указанной цепочки. Ошибка резервного звена не отвергает исправный основной профиль. Если основной профиль не подготовился, используется первое успешно подготовленное звено; при ошибке во время игры переключение идёт только на уже подготовленный резерв. Скрытого перехода на произвольного трекера нет. Без резерва или после исчерпания цепочки ошибка запуска даёт HTTP 400; ошибка работающего бота либо reset при реванше останавливает локальный матч с понятным сообщением и возвращает состояние `none`/`idle`. После этого доступны выбор другого бота и LAN.

При замене соперника снимок сохраняет `requestedBotId`/`requestedBotName` выбранного профиля и `effectiveBotId`/`effectiveBotName` фактического. `opponentFallbackActive` показывает различие ID, `botFallbackReason` объясняет причину. Реванш сохраняет выбранную идентичность и уже действующий резерв, не возвращаясь к профилю с зафиксированной ошибкой; новый отказ может продвинуть цепочку дальше. Выход очищает идентичность сессии и сообщение о её fallback, но не сбрасывает известную доступность процесса. Доступная ранее выбранная карточка остаётся выбранной в открытой вкладке — это отдельное состояние UI.

## HTTP: обнаружение, запуск, реванш и выход

Запросите каталог, затем передайте **точный** case-sensitive ID. Сервер не обрезает пробелы и не приводит ID к нижнему регистру. Человеческий `nickname` обязателен: после обрезки внешних пробелов 1–24 единицы UTF-16, без управляющих символов. Бот может иметь имя до 64 единиц и не занимает `peerNickname`.

```sh
curl --fail-with-body http://127.0.0.1:5080/api/bots
```

Сначала покиньте текущий матч, LAN-лобби или поиск игры. Новый бот допускается только из состояния `none`/`idle`. Неизвестный или отключённый ID, попытка активной замены либо невозможность подготовить ни одного звена выбранной явной цепочки дают HTTP 400 без замены текущего матча. Основной профиль в состоянии `unavailable` может успешно запуститься через пригодный настроенный резерв; `notChecked` допускает попытку подготовки.

```sh
curl --fail-with-body -X POST http://127.0.0.1:5080/api/leave \
  -H 'Content-Type: application/json' -d '{}'
curl --fail-with-body -X POST http://127.0.0.1:5080/api/local-opponent \
  -H 'Content-Type: application/json' -d '{"nickname":"Игрок","botId":"sokol"}'
curl --fail-with-body http://127.0.0.1:5080/api/status
curl --fail-with-body -X POST http://127.0.0.1:5080/api/restart \
  -H 'Content-Type: application/json' -d '{}'
curl --fail-with-body -X POST http://127.0.0.1:5080/api/leave \
  -H 'Content-Type: application/json' -d '{}'
```

У успешного `sokol` режим `bot`, оба ID равны `sokol`, оба имени — `Сокол`, `peerNickname: null`, `opponentFallbackActive: false`, `botFallbackReason: null`. Реванш увеличивает `roundId`, сбрасывает счёт и начинает countdown. После выхода все строки идентичности и причины бота равны `null`, флаг fallback — `false`. В LAN `requestedBotId`, `requestedBotName`, `effectiveBotId`, `effectiveBotName` и `botFallbackReason` также равны `null`, `opponentFallbackActive` — `false`, а `peerNickname` снова обозначает человека.

## Миграция клиентов и старых настроек

Обновляйте сервер и браузер совместно; старая открытая вкладка должна перезагрузить новую сборку. Текущие HTTP-снимки, каталог и браузерный MessagePack используют обязательную версию **8**. Старые значения режима `simple`/`hard` и поле снимка `requestedOpponentMode` удалены. Запрос только с `{nickname, mode}` больше не задаёт профиль: `botId` обязателен. Если корректный `botId` передан вместе с лишним старым `mode`, выбор определяется `botId`. Отсутствующий `botId` не выбирает профиль по умолчанию. Общий `opponentMode` принимает `none`, `lan`, `bot`; бинарные значения — 0, 1, 2.

WebSocket-снимок содержит **30 полей**. Индексы 0–22 сохраняют прежний порядок; хвост имеет следующий вид:

| Индекс | Поле                     |
| ------ | ------------------------ |
| 23     | `opponentMode`           |
| 24     | `requestedBotId`         |
| 25     | `requestedBotName`       |
| 26     | `effectiveBotId`         |
| 27     | `effectiveBotName`       |
| 28     | `opponentFallbackActive` |
| 29     | `botFallbackReason`      |

Управление — одно MessagePack-значение `[8, axis]`, где `axis` равен -1, 0 или 1. `peerNickname` в бот-матче равен `null`; имена ботов берутся из отдельных полей. Nullable-поля присутствуют в HTTP JSON; отсутствующие значения передаются как JSON `null` и MessagePack `nil`. UDP-протокол LAN остаётся отдельным протоколом версии 8; эта миграция каталога его формат не меняет.

Переменная `LANPONG_HARD_MODEL_PATH` больше не управляет игровым ботом. Перенесите путь в `Bots.Entries[index].Onnx.ModelPath` или точечный override `Bots__Entries__2__Onnx__ModelPath` для исходного `vektor`, согласуйте `ExpectedSha256` и перезапустите процесс. Сохранённые `--hard-smoke`/`--hard-benchmark` относятся к отдельной legacy-диагностике и не доказывают работу выбранного каталожного профиля; инструменты обучения и их результаты остаются отдельными.

## Проверить конфигурацию без запуска сети

Из папки опубликованного приложения после добавления примера можно проверить и явный `sokol`, и default. Эти команды используют те же источники конфигурации и фабрики, создают и освобождают подготовленную сессию, но не запускают игровой peer или сетевой listener:

```sh
./LanPong --bot-benchmark sokol --benchmark-samples 100 --benchmark-warmup 2 \
  --environment Production --contentRoot "$PWD"
./LanPong --bot-benchmark --benchmark-samples 100 --benchmark-warmup 2 \
  --environment Production --contentRoot "$PWD"
```

При `DefaultBotId: sokol` оба JSON-отчёта должны показать `requestedBotId = effectiveBotId = sokol`, `strategyId = tracker`, `cadenceTicks = 7`; для трекера `verifiedModelSha256` равен `null`. Диагностика отвергает fallback, смену идентичности, исчерпанную сессию и недопустимую ось, возвращая ненулевой код без отчёта. Ошибки конфигурации сохраняют имя проблемного параметра.

100 samples / 2 warmup — короткая проверка примера, не основание для выводов о производительности. Для измерений используйте воспроизводимые команды и ограничения из [performance.md](performance.md). `dynamicCodeSupported` описывает возможность runtime, а не устанавливает managed/Native AOT режим; режим подтверждается способом запуска и публикацией. Нулевые calling-thread managed allocations не означают отсутствие native allocations, утечек или задержек полного игрового тика.
