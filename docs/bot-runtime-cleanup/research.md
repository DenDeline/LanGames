# Research and architectural decisions

## Repository evidence before implementation

The project already uses .NET 10/C# 14, source-generated configuration binding and JSON, typed validated options, immutable catalog lookup and Microsoft.ML.OnnxRuntime 1.30.0. No additional runtime library is needed to remove duplicate policies or reorganize files. Retain the established configured factories and explicit session fallback rather than introduce a second plugin/DI architecture.

`HardLocalOpponentController.cs` contains two different responsibilities: a legacy implicit-fallback controller and the warmed inference adapter still used by the supported strict ONNX policy. Remove the controller while extracting the inference interface/adapter and frozen-model contract into canonical production types. `SimpleLocalOpponentController` already accepts tracker settings; make that the sole named tracker implementation. Defaults and observation schema belong to canonical settings/model contracts, independent of an old controller class.

Live callers include options defaults, factories, configured diagnostic/model identity, catalog/session/controller tests, training baselines and `EvaluatedModelPolicy`'s production evaluator. A simple delete or moving legacy controllers into tools would leave duplicate behavior or break these consumers. Canonical training evaluation must use the supported strict model policy and fail explicitly when the model is invalid; session fallback belongs only to the configured runtime.

Dependency review refines step 1: delete the directly obsolete Hard diagnostic class, Hard flags and published smoke hooks alongside their removed controller, rather than rewriting obsolete diagnostic entry points. The remaining tiny/configured probes are isolated in step 3. Current real-catalog smoke starts Vektor and leaves during countdown, so it must be strengthened to healthy cadence-advanced Playing with matching WebSocket identity to preserve actual production inference proof. Do not preserve legacy controller wrappers or legacy runtime fallback for compatibility.

The ONNX POSIX telemetry guard is required by the production native runtime and remains production code. `Models/hard-v1.onnx` is the valid trained artifact; its historical filename, digest and observation schema are not duplicate controllers and need no gratuitous rename. The tiny `aot-smoke.onnx` probe is tool/test-only and must leave the production payload.

The pre-existing `System.Threading.Lock` edit is user state. The runtime migration must preserve it, including the nested availability-read locking used by catalog discovery, and record its inclusion instead of discarding or disguising it.

## Tooling boundary

A separate diagnostics/benchmark executable may reference the supported runtime project, but the production app must not reference developer tools or BenchmarkDotNet. Explicit internal visibility for tools is preferable to promoting implementation types into an unnecessary public API. The source, build/reference graph, production entry point and published payload must all demonstrate exclusion. A string search of a trimmed native executable alone is too weak to prove the project boundary.

Published production validation must start a configured model through the real public API and verify actual effective identity, gameplay/axis evidence, fallback and lifecycle. A separate tool smoke does not prove the app's normal production path works. Generated binding/JSON and Native AOT still require a real application publication.

## Compact mode and opponent UX

Chess.com's official help describes separate online/bot entry points, optional settings revealed by Custom Challenge, and a game-type dropdown. Bot selection precedes Play, and practice offers Change Bot. These support progressive disclosure; the exact LanPong three-mode dropdown is an adaptation, not a claim to reproduce its undocumented implementation. Sources: [starting games](https://support.chess.com/en/articles/8609779-how-do-i-start-a-game-on-chess-com), [bot selection](https://support.chess.com/en/articles/8614091-how-can-i-play-against-the-chess-com-bots), [changing a practice bot](https://support.chess.com/en/articles/8572788-how-can-i-play-the-computer-from-a-custom-position).

Step 4 should use a labeled native select with bot, quick LAN and join LAN modes, showing only the relevant setup. Changing setup never starts/cancels a session. Shared nickname and join details persist; mode/selection are disabled during busy/active sessions. Challenge/session/rematch/leave/fallback remain outside the setup panels.

Bot setup becomes a compact name/avatar/difficulty/readiness summary, Change button and one named Play. The grouped native radios and full profile move into a native modal dialog; radio changes take effect immediately, while Done/Close/Escape dismiss without launching a match. Clear paddle input on open and exclude all open-dialog descendants from global keyboard handling. Focus the eligible selected radio when opening, return to the opener on close, and never move focus into a closed picker on catalog refresh. Preserve retry/empty/all-unavailable, truthful configured fallback, node stability and accepted exact-bot/round action guards.

Record the old panel height before editing. For the normal bundled/default state, target a total selection panel no taller than 400px desktop / 440px at 320–390px and at least 50% lower than baseline. Closed-picker height must not grow with catalog size. Long names and failure reasons may expand naturally rather than be clipped. The dialog is about 600px wide desktop, viewport minus 24px on phones, with bounded dynamic-viewport height and scrollable contents; Close/Done remain reachable.

Native [select](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/select) and [dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/dialog) fit the existing stack; follow [W3C modal focus guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). A native opponent select is compact but offers little room for full profiles and unavailable reasons. [Lit](https://lit.dev/docs/) and [Web Awesome dialog](https://webawesome.com/docs/components/dialog) are viable but introduce unnecessary rendering/styling dependencies; [Shoelace](https://shoelace.style/) is sunset. No new frontend library is justified.

Read-only source review adds concrete integration gates. Active means host/guest or searching, including waiting, challenge, disconnected and game-over states; setup stays locked throughout. Sharing currently lives inside quick setup, so a fresh tab observing an existing host must expose LAN context despite the bot default. Keep challenge/cancel/session controls reachable outside hidden setup. Invalidate deferred picker focus on close, mode change or active snapshots; asynchronous close focus must not override accepted arena focus. Keep Change/retry reachable when all bots are unavailable, disabling Play separately. Mode/picker presentation must participate in rendering or update independently; ordinary snapshots keep nodes, selection and focus stable. Use explicit button types, no nested forms, and preserve native closed-dialog/hidden semantics.

Measure baseline and final idle `.connect-panel` under identical catalog/font/zoom conditions at 1366×900, 390×844 and 320×800. Inspect 1024px layout, extra entries, maximum-length reasons and 64-character unbroken names separately. Verify mode changes issue no requests and retain nickname/join details; native dialog radio/Tab/Escape/return focus and input suppression; retry completing after close; active snapshot while picker is open; fresh-tab host sharing; actual discovery/manual join; and existing exact-bot/round action races. Fake-DOM fixtures cannot establish native modal/keyboard behavior, so real browser evidence is required.

## Production project and publish boundaries

Independent dependency review accepts a one-way developer tool/benchmark to app reference, following the existing training-tool pattern. Narrow `InternalsVisibleTo` access avoids a public runtime API and does not create an app-to-tool dependency. Match executable-reference/self-contained settings deliberately for any published AOT tool. A separate engine/library split is unnecessary for this goal.

The SDK includes app-subfolder C# files through default globs; moving diagnostics into `src/LanPong/Diagnostics/` would still compile them. Review evaluated app Compile/Content/ProjectReference items and its resolved package graph, absence of dispatch in Program, a fresh publication denylist, and successful normal production gameplay together. A missing diagnostic DLL or native-binary string search alone cannot prove exclusion. Keep release jobs publishing the app project directly, and strengthen real-model play checks for every release RID. Sources: [SDK default items](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/overview), [MSBuild project/reference properties](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props), [publish behavior](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-publish), [Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/).

Extraction must move the configured report types and generated report JSON context with their diagnostics, relocate the tiny model and generator default outside the app, and update wrong-schema test fixtures. Keep useful probes in a dedicated one-way developer executable. Its entry point must explicitly call `OnnxRuntimeStartup.DisablePosixTelemetry` before direct ONNX access: merely referencing the app does not establish that its module initializer ran before a tool-only ORT path. The existing training entry point demonstrates this explicit guard. Retain the built-but-unstarted `WebApplication` and normal ASP.NET configuration providers/ownership for configured probes. Bound the shared Node decoder subprocess so published smoke cannot hang on fixture decoding; keep its imported integration runner inert. Production smoke must no longer invoke removed diagnostic flags.

Review requires precise publish exclusions: known developer assembly/package names and exact result/tool directories, not arbitrary `training`, `diagnostics` or `reports` substrings that reject legitimate custom models/static/framework files. Tool help must use a verified absolute content-root example: default cwd and explicit relative roots have different rules, and explicit relative roots resolve against AppContext.BaseDirectory. Preserve the normal framework behavior rather than introducing a custom resolver. [Framework root resolution](https://github.com/dotnet/runtime/blob/release/10.0/src/libraries/Microsoft.Extensions.Hosting/src/HostBuilder.cs#L200-L234).

## BenchmarkDotNet decision and review gates

Use a permanent `benchmarks/LanPong.Benchmarks` console coverage project on existing net10.0/C# 14, with BenchmarkDotNet referenced only there. Research found latest stable 0.15.8; 0.16 entries are previews. The worker must let `dotnet add package BenchmarkDotNet` resolve the current stable compatible version and retain it through existing central package management. No benchmark package may enter the production graph. The managed host has PublishAot=false; BDN generates separate native children. Sources: [NuGet package](https://www.nuget.org/packages/BenchmarkDotNet), [.NET 10 Native AOT normalization fix](https://benchmarkdotnet.org/changelog/v0.15.6.html), [Native AOT toolchain](https://benchmarkdotnet.org/articles/configs/toolchains.html#nativeaot).

Comparison matrix: three shipped configured IDs times consecutive/cadence-spaced calls is six CoreCLR cases; adding independently validated .NET 10 Native AOT gives twelve. This compares decision frequency and runtime on identical supported policies as a regression baseline, not historical refactor speedup or opponent strength. Use one public instance benchmark on a public nonsealed class, returning one GetAxis result per invocation with operation count one. BDN controls calibration/warmup: no manual timing/allocation loops or iteration-reset scheme. Prebuild a varied Playing-state ring in GlobalSetup, but keep the long tick increasing even when the ring wraps across pilot/warmup/actual phases; spaced ticks remain cadence multiples.

Setup must resolve real configured factories/catalog under explicit Production with a valid content root, verify requested/effective identity, playable session and actual configured model digest, and ensure generated children have config/model/native assets. Consistent light per-operation guards reject illegal axes/fallback/identity changes instead of reporting fast degraded runs; disclose their measured overhead. GlobalCleanup owns both prepared session and unstarted configuration host, with partial-setup failure cleanup. Different calibrated invocation counts mean final checksums need not match across jobs. [Setup and cleanup behavior](https://benchmarkdotnet.org/articles/features/setup-and-cleanup.html).

Pass args through BenchmarkSwitcher and always supply a filter. Validate all managed cases with Dry, then independently validate native cases with `--runtimes nativeaot10.0`, native-build logs and ARM64 executable provenance. An earlier app AOT publish does not prove a BDN child works. Then run one representative Vektor cadence case normally and review its report before the bounded serial final matrix. `--runtimes net10.0 nativeaot10.0` establishes the CoreCLR runtime baseline; matched-invocation comparisons using `--apples` require explicit iteration counts. Retain logs and Markdown/full JSON in distinct artifact directories with --noOverwrite and propagate any validation/case failure. Sources: [Native AOT platforms](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#platformarchitecture-restrictions), [runtime API](https://benchmarkdotnet.org/api/BenchmarkDotNet.Environments.NativeAotRuntime.html).

Use MemoryDiagnoser for managed allocations and verify actual native-job output. NativeMemoryProfiler is Windows-only and is unsuitable here. Review mean/error/standard deviation, operation/allocation units, job settings and warnings. BDN percentile columns describe normalized iteration measurements, not individual GetAxis latency tails. Neither managed allocation counts nor these timings prove native memory/leak freedom or a whole game-tick bound. [Diagnoser restrictions](https://benchmarkdotnet.org/articles/configs/diagnosers.html#restrictions).

The independent reviewer read the microbenchmarking skill and all relevant setup, authoring, comparison, diagnoser and tuning references. Worker authoring/review must use those current references; old assumptions about runtime names/CLI/configuration are insufficient.

Additional read-only 0.15.8 API/source inspection refines implementation gates. `ExecuteResult.IsSuccess` alone only establishes workload/result measurements, so also reject missing executable, nonzero child exit, recorded errors, failed reports, absent statistics/result runs, critical validation and missing expected cases. Derive the expected parameter/runtime-expanded case set before execution using the current public filtering APIs; summary case collections themselves derive from returned reports and cannot prove skipped-case coverage. Intentionally empty help/version/valid list/info commands may succeed, while malformed arguments and zero-match execution must fail. Verify those entry-point behaviors with focused CLI probes.

Generated managed children run in their generated output directory, while native children can inherit host cwd; application configuration arguments are not forwarded to them. Setup therefore needs an explicit Production content root backed by canonical copied assets or a documented environment path, independently of cwd. Validate child config, frozen model and native library rather than assuming project-reference propagation. Native jobs define their generated `NATIVEAOT` harness macro; no manual host macro is required.

The generated benchmark child has its own entry point and does not execute the coverage project's host Program. Apply the shared ONNX telemetry guard in GlobalSetup before model preparation/direct ORT access, rather than relying only on a parent-host call. Keep it outside measurement and preserve setup-failure disposal.

Matched-invocation `--apples` is optional and changes measurement semantics in 0.15.8: it forces one warmup, disables overhead evaluation and outlier removal, and shares baseline-calibrated invocation counts. If used, disclose those actual settings and inspect confidence/error rather than presenting it as default steady-state confidence. Keep a representative default run and a bounded serial final comparison; do not combine separate job modes into a false speedup claim.

Prefer conventional final comparison settings: one launch, six warmups, fifteen actual iterations and 250ms iteration target, across the twelve selected cases after Dry/native validation and the representative default run. Retain default operation units and BDN calibration; inspect actual report settings and warnings. Exact standalone help may succeed; mixed help/invalid arguments must fail, while successfully parsed list/info remains non-executing. Current source/API evidence: [Summary](https://benchmarkdotnet.org/api/BenchmarkDotNet.Reports.Summary.html), [BenchmarkReport](https://benchmarkdotnet.org/api/BenchmarkDotNet.Reports.BenchmarkReport.html), [ExecuteResult](https://benchmarkdotnet.org/api/BenchmarkDotNet.Toolchains.Results.ExecuteResult.html), [ConfigParser](https://benchmarkdotnet.org/api/BenchmarkDotNet.ConsoleArguments.ConfigParser.html), [pinned switcher implementation](https://raw.githubusercontent.com/dotnet/BenchmarkDotNet/1e8238ef6c08e18821edae83ac8d6b0a2bb1bb98/src/BenchmarkDotNet/Running/BenchmarkSwitcher.cs), [pinned argument definitions](https://raw.githubusercontent.com/dotnet/BenchmarkDotNet/1e8238ef6c08e18821edae83ac8d6b0a2bb1bb98/src/BenchmarkDotNet/ConsoleArguments/CommandLineOptions.cs). One-launch results establish a local baseline, not a portable regression threshold or individual-call latency tail.
